# Дизайн: модуль «Диадок» — учёт пользователей и прав из ручных выгрузок

Дата: 2026-11-18
Статус: на согласовании (прошёл builder check, правки внесены)

## Зачем

Реестр отвечает на вопрос «кто есть кто и у кого какой доступ». Сейчас в нём нет операторов
ЭДО (Диадок): кто подписывает, кто согласует, кто админ в какой организации группы.
Специалист выгружает из Диадок реестр пользователей **вручную** (xlsx, **по одной организации
на файл**, структура — как в «Диадок Общий Реестр.xlsx») и загружает файл в реестр. Реестр
должен: хранить актуальный срез, привязывать учётки к сотрудникам, участвовать в ролевой
модели («положено/есть», SoD, привилегированный доступ), напоминать, когда загрузка устарела.

## Цели / не-цели

Цели:

- раздел «Диадок» в реестре: организации → пользователи с правами (флаги), привязка к `Person`;
- ручная загрузка xlsx специалистом с карточки организации, с предохранителем и журналом;
- дата последней загрузки зафиксирована на карточке организации и видна в разделе;
- напоминания о просроченной загрузке (настраиваемое правило уведомлений, email + колокольчик);
- права Диадок — полноценные `Entitlement` системы «Диадок»: сверка «положено/есть», SoD,
  списки «Лишнее/Не хватает» и reconcile-часть «Привилегированного доступа» видят Диадок
  через `access_roles/engine.py`.

Не-цели (этап 1):

- реестр не читает Диадок по API и ничего туда не пишет (инвариант 1) — только приём файла;
- чек-листы по кадровым событиям и заявки на доступ к Диадок;
- склейка с юрлицами (`Legal Entity`) по ИНН — в выгрузке нет ИНН, только название организации.

Анти-цели: «тихая» потеря учёток при загрузке не той/обрезанной выгрузки; раздел, видный
без права на систему «Диадок»; ФИО/даты рождения в журналах загрузки (инвариант 3).

## Формат выгрузки

Подтверждён по реальному образцу (37 организаций, ~380 пользователей; ФИО местами КАПСОМ,
у части пользователей логин «—», есть технико-учётки вроде Entera EDI, один человек может
быть в нескольких организациях с разными логинами).

Лист: строка заголовков (не обязательно первая) и колонки:

| Колонка | Поле |
|---|---|
| Компания | организация Диадок |
| ФИО | полное имя |
| Должность | должность |
| Логин | email или «—» |
| Логин акт. | учётка активна (bool) |
| Админ | администратор организации (bool) |
| Заблок. | учётка заблокирована (bool) |
| Подпись | право подписи (bool) |
| Госключ | право использовать Госключ (bool) |
| Согл. | право согласования (bool) |
| Запрос согл. | право запрашивать согласование (bool) |
| Черновики | создавать/редактировать документы и черновики (bool) |
| Удаление | удалять/восстанавливать документы (bool) |
| Платежки | создавать и отправлять платежки в банк (bool) |
| Контрагенты | работа с разделом «Контрагенты» (bool) |

Колонки правее «Контрагенты» — легенда (расшифровка флагов), игнорируются. Парсер ищет
колонки **по именам заголовков** (нормализованно: регистр, пробелы, точки), не по позициям;
bool принимает `True/False/Истина/Ложь/1/0/Да/Нет`. Файл штатно — по одной организации,
но загрузчик терпит и общий реестр (несколько организаций): организации из файла
автосоздаются (см. ниже), пометка пропавших действует только на организации, присутствующие
в файле.

## Подходы

Выбрано: **A + C в одном этапе** (решение заказчика, 2026-11-18).

- A. Полноценный модуль-источник `diadoc` по образцу `file_shares` (DocTypes, загрузка,
  предохранитель, Sync Log, привязка к Person, раздел в `/registry`). Отвергнуты: B (только
  админка без раздела в `/registry` — нет видимого раздела для пользователей) и
  «C отдельным этапом» (заказчик попросил сразу с ролевой моделью).
- C. Права Диадок как `Entitlement` системы «Диадок»: ключи `dd:<орг>|<право>` в
  `raw_accesses`, новые поля в `Entitlement`, участие в сверке/SoD.

## Решения по устройству

### Модуль и DocTypes

Новый модуль Frappe `Diadoc` (`access_registry/diadoc/`, добавить в `modules.txt`).

- `Diadoc Organization` — организация Диадок. Поля: `name` (title, см. про ключ),
  `last_upload`, `last_status`, `upload_reminder_days` (порог свежести, по умолчанию 30),
  `enabled` (участвует в напоминаниях), `comment`. Связь с `HR Organization`/`Legal Entity`
  не делаем (в выгрузке нет ИНН). `Sync Log.source` оставляем пустым (это Link на `Info Base`,
  как у file_shares).
- `Diadoc User` — пользователь в организации. Имя (ключ): `<орг>:<логин>` при валидном
  логине (не «—»), иначе `<орг>:фио:<нормализованное ФИО>` (`normalize_name`). Поля:
  `organization` (Link), `full_name`, `position`, `login`, флаги: `login_active`, `is_admin`,
  `blocked`, `can_sign`, `gov_key`, `can_approve`, `can_request_approve`, `drafts`,
  `can_delete`, `payments`, `counterparties`; привязка: `person`, `person_link_method`,
  `person_link_note`, `manual_person`; `src_hash`, `missing_in_source`, `uid`.

**Ключ организации.** Стабильного ID в выгрузке нет, устойчивость — по нормализованному
названию (регистр, кавычки, пробелы; «ООО "Ромашка"» = «ромашка»). Организации
**автосоздаются из файла** (по образцу HR Organization), специалист не заводит 37 карточек
руками. Переименование организации в Диадок = старая помечается «нет в выгрузке», новая
создаётся, в Sync Log — предупреждение. Ручная склейка не делается (нет ID) — принятое
ограничение (моё решение).

Оба DocType: `track_changes`, права — System Manager, Registry Admin (полные), Registry
Auditor (чтение), новая роль «Диадок: специалист» (загрузка и чтение модуля; создаётся
в `install.create_roles`, константа в `permissions.py`).

### Загрузка

- Whitelist `access_registry.diadoc.api.upload()` — POST. Аргумент: файл xlsx (base64 JSON;
  Desk-кнопки достаточно). Проверка роли: админы + «Диадок: специалист» (`require`).
- UI: на карточке `Diadoc Organization` поле-вложение «Файл выгрузки» (Attach) и кнопка
  «Загрузить выгрузку» (client script): читает файл, вызывает `upload`. Результат — статус
  Sync Log и счётчики сообщением. (Кнопка и на списке организаций — открыть карточку с файлом.)
- Ядро `diadoc/sync.py::run_upload(bytes)` по образцу `file_shares/sync.py`: парсинг →
  один savepoint → предохранитель → пометка пропавших **только в рамках организаций,
  присутствующих в файле** → Sync Log (вид «Диадок» — добавить опцию в `Sync Log.kind`)
  → `last_upload`/`last_status` на организациях из файла. `_switch_user` на пользователя
  синка, `_format_messages` с redact, личные данные в сообщения не пишутся.
- Предохранитель: для каждой организации из файла — если в файле существенно меньше
  пользователей, чем актуальных в реестре (общий порог `shrink_threshold_pct`), загрузка
  откатывается целиком. Минимум — свой, Diadoc-specific: защита работает с 3 записей
  в реестре (пример: в реестре 5 учёток, в файле 2 — сокращение 60% > порога, откат).
  Глобальный `guard_min_records = 20` не подходит: большинство организаций Диадока
  маленькие, и с ним защита не сработала бы никогда. Организации с 1–2 учётками
  предохранитель не защищает (там не отличить обрезок файла от легитимного удаления).
  При первой загрузке (в реестре по организации нет записей) предохранитель не применяется.
  Первая загрузка — это общий реестр на десятки организаций: всё создаётся, организации
  автосоздаются, смотри «Ключ организации».
- Парсер `diadoc/parser.py`: openpyxl (зависимость Frappe), поиск шапки по имени колонки,
  bool-нормализация, легенда справа игнорируется. Дубликаты ключа в файле — предупреждение,
  берётся последняя строка (по образцу `index_rows`). Не распозналась шапка/обязательные
  колонки — `ParseError`, откат.
- После успешной загрузки — явный пересчёт счётчиков прав (`engine.refresh_counters()`;
  плановый пересчёт иначе только ночью, а списки/отчёты после загрузки должны быть
  актуальными).

### Привязка к сотруднику (`Diadoc User.person`)

По образцу `access_catalog/linking.py` и B24 User, порядок:

1. `manual_person` (всегда главнее, загрузка не трогает);
2. логин-email → `AD Account` по `user_principal_name` → его `person`;
3. тот же email → `B24 User.email` → его `person`;
4. ФИО через `NameMatcher` (нормализация регистра/ё, КАПС не мешает), среди однофамильцев
   выигрывает единственный работающий.

Способ и причина неудачи — в `person_link_method`/`person_link_note`. Учётки с логином
«—» привязываются только по ФИО.

### Ролевая модель (вариант C)

- `Entitlement.system` — добавить опцию «Диадок» (прецедент: опции сейчас
  `1С/Active Directory/Битрикс24/Другое`). Новые поля: `dd_organization`
  (Link → `Diadoc Organization`, **необязательное: пусто = любая организация** — по
  прецеденту пустого `b24_portal`/`bit_base`; иначе поддерживать 9 прав × N оргов руками)
  и `dd_right` (Select: Подпись / Госключ / Согл. / Запрос согл. / Черновики / Удаление /
  Платежки / Контрагенты / Админ).
- Ключи «есть» в `engine.raw_accesses`: `dd:<organization>|<dd_right>`. Источник —
  `Diadoc User`, где `login_active=1`, `blocked=0`, `missing_in_source=0`, `person` задан,
  соответствующий флаг = 1. Состояния «Логин акт.»/«Заблок.» правами не являются.
- Ветки `dd:` в `engine.entitlement_keys` (для пустой `dd_organization` — ключи по всем
  организациям, как у bit/b24), `engine.describe_key` (заголовок «Диадок <орг>: <право>»).
  `describe_key` для `dd:...|Админ` возвращает `privileged=1` явно (`PRIVILEGED_WORDS`
  само срабатывает только в `ensure_entitlement` при подборе ролей — ручные записи
  обязаны ставить флаг сами).
- После загрузки Диадок — пересчёт держателей прав (см. «Загрузка»).

### Контрольные списки: что автоматически, что вручную

Через engine бесплатно: «Лишние доступы», «Не хватает доступов», «Конфликты полномочий»,
reconcile-часть «Привилегированного доступа» (моё уточнение после проверки: список
«Доступ у неработающих» — это жёсткий SQL-union `_control_dismissed`, **не engine**).

Явные доработки в `registry/api.py`:

- `_control_dismissed` — новая ветка union: активная (не заблокированная) учётка Диадок
  у сотрудника со статусом «Уволен» (и не «не работает»-состояния — по образцу существующих
  веток);
- список «Учётки без сотрудника» — ветка с пользователями Диадок без `person`
  (по образцу существующих веток списка).

### Напоминания о загрузке

Новое событие в `notify.py`: «Диадок: пора загружать выгрузку» (новая опция Select в
`Registry Notification Rule.event`). Коллектор: организации с `enabled=1`, у которых
`last_upload` отсутствует или старше `today - upload_reminder_days`. Текст:
«<орг>: последняя загрузка <дата>/ещё не загружалась». Администратор создаёт обычное
«Уведомление» (получатели — специалист, каналы email/колокольчик, частота). Видимость:
не через разделы `/registry`, а по праву чтения `Diadoc Organization` — специалист
работает в Desk и может не иметь доступа к `/registry` (иначе, как у SOURCES, коллектор
молча не отдал бы ему элементы). Ссылка в письме/колокольчике — на Desk-список
`Diadoc Organization`. (Моё решение; если специалисту дадут профиль `/registry` —
увидит и раздел «Диадок» тоже.)

Дайджест (`digest.source_problems`) не трогаем: его порог свежести 26 часов для ручного
ежемесячного источника давал бы ложные «проблемы» ежедневно.

### Приложение `/registry`

- `app_access.SYSTEMS["dd"] = "Диадок"`, `SYSTEM_OF_LABEL["Диадок"] = "dd"` — система
  ограничивается в профилях доступа как остальные; списки, поиск и карточка уважают
  ограничение. Метка системы пронизывает проект — чек-лист мест (проверено по коду):
  `registry/metrics.py` (`SYSTEMS`), `www/registry.js` (`MGMT_SYSTEMS`, навигация,
  `seesSystem`), `registry/api.py` (метки в `people()`, `SYSTEM_OF_REF`, `SOURCE_SYSTEM`,
  `search()`), поле `s_diadoc` в DocType профиля доступа.
- Новый раздел `SECTIONS["diadoc"] = "Диадок"`: каталог организаций (свежесть загрузки:
  дата, просрочка подсвечивается) → пользователи организации с флагами и привязкой.
  API — новые методы в `registry/api.py`; согласно AGENTS.md новые разделы выносить
  в отдельные модули (например `registry/diadoc_api.py`).
- Карточка 360°: блок «Диадок» в учётных записях (`person()` добавляет `dd`-блок,
  `registry.js` — в `MGMT_SYSTEMS` и рендеринг), счётчики `accounts_dd`/`linked_dd`
  в «Сотрудниках».

### Workspace, права, регистрация

- Новый workspace «Диадок»: списки `Diadoc Organization`, `Diadoc User`, отчёты модуля,
  ссылка на Sync Log. Workspaces пересобираются из JSON репозитория при каждом migrate
  (`install.sync_workspace`); тест `test_workspace.py` требует ссылок на оба новых DocType.
- `permissions.py`: константа роли «Диадок: специалист»; `upload` требует её (или админа);
  чтение модуля — по аналогии с другими источниками (READERS + специалист).
- `hooks.py`: отдельный cron не нужен (загрузка ручная; счётчики — переиспользуем
  существующий `access_roles.api.scheduled_refresh`).
- `install.py`: создание роли через `create_roles`.

### Отчёты (этап 1)

Query Report по образцу существующих: «Пользователи Диадок» (орг, ФИО, логин, флаги,
сотрудник, способ привязки), «Диадок: администраторы». Регистрируются в workspace модуля.

### Тесты и инварианты

- `bench --site <site> run-tests --app access_registry`; CI `.github/workflows/ci.yml`;
  `ruff check` + `ruff format --check`.
- Тесты по образцу тестов загрузок file_shares и `test_notify.py`: парсер (шапка не в
  первой строке, легенда, bool-форматы, логин «—», автосоздание организаций), загрузка
  (создание/изменение/пометка пропавших только своей организации, предохранитель,
  откат, пересчёт счётчиков), привязка к Person (4 способа + manual выигрывает), ключи
  engine (`dd:` в raw_accesses/entitlement_keys/describe_key, неактивные/заблокированные
  не считаются, «любая организация»), напоминания (порог по дням, never-loaded,
  видимость для специалиста без `/registry`), ветки контрольных списков
  (неработающий с активной учёткой, без сотрудника), workspace-ссылки.
- Инварианты: в Диадок не пишем никогда; POST-only для изменяющих действий; ФИО/даты
  рождения не в Sync Log; каждый метод API сам проверяет права; ручные поля
  (`manual_person`) загрузка не перезаписывает.

## Решения, принятые автором дизайна (мои допущения — проверить при чтении)

1. Порог свежести по умолчанию `upload_reminder_days = 30`; настраивается на карточке
   организации.
2. Роль специалиста — «Диадок: специалист» (Desk; без `/registry` по умолчанию).
3. Ключ организации — нормализованное название; автосоздание из файла; склейки при
   переименовании нет (нет устойчивого ID).
4. «Админ» — единственный флаг-состояние, который является правом (привилегированным,
   флаг ставится явно). «Логин акт.» и «Заблок.» — только состояния.
5. Права учитываются в «есть» только у активных незаблокированных учёток с привязанным
   сотрудником (как в 1С/AD/B24).
6. У `Entitlement` Диадок организация необязательна: пусто = любая (прецедент Битрикс24).
7. Предохранитель Диадок срабатывает с 3 записей в реестре (а не с глобальных 20);
   при первой загрузке организации не применяется; первая загрузка — общий реестр
   на множество организаций, всё автосоздаётся.
8. Дайджест не показывает Диадок; напоминания — только через настраиваемое правило
   уведомлений (email + колокольчик).
