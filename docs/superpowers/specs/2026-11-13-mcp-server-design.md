# MCP-сервер для Картотеки: дизайн

Дата: 2026-11-13
Статус: реализовано (документ задним числом фиксирует принятые решения)

## Зачем

Агенты (Claude Desktop, Kimi Code, n8n-агенты и т.п.) должны уметь работать с реестром
доступов: анализировать, у кого какие доступы, искать излишние/недостающие права и
**предлагать роли доступа для сотрудников** — на основе типового доступа должности,
уже существующих ролей и сверки «положено / есть». Сегодня для этого нужен браузер
и ручной клик по `/registry`.

## Цели

- Агент по имени сотрудника получает его полную картину доступов (360°) одним вызовом.
- Агент видит каталог ролей, прав (entitlements), процессов, контрольные списки
  (лишнее/недостаёт/SoD/привилегированные) и отчёты, включая role mining.
- Агент может запросить обоснованное предложение ролей для конкретного сотрудника:
  какие существующие роли покрывают его типовой доступ и текущие «не хватает».
- Всё это — без записи в реестр: агент анализирует и предлагает, человек решает.

## Не-цели (v1)

- Запись через MCP: создание ролей, назначения, гашение замечаний, планы AD — нет.
  Изменяющие действия остаются POST-методами API с проверками прав и «четырьмя глазами».
- Отдельный UI или хранение данных вне реестра: сервер — тонкий адаптер, всё состояние
  в Frappe.
- Транспорт HTTP/SSE для удалённых агентов (можно добавить позже одной строкой).

## Анти-цели

- Обход проверок прав реестра. Сервер MCP не имеет собственной авторизации и не
  расширяет права: он действует от имени выделенного пользователя Frappe, и все
  серверные проверки (`permissions.py`, `app_access.py`) остаются обязательными.
- Персональные данные (даты рождения, отсутствия) в выдаче агенту: пользователь сервера
  — с ролью читателя, не аудитора, значит `person()` сам режет персональные поля
  (инвариант 3).

## Подходы

1. **Отдельный MCP-сервер (Python, FastMCP, stdio), ходит в Frappe по REST с API-ключом.**
   Стандартный транспорт для локальных агентов; ноль изменений в приложении; проверки
   прав остаются в реестре; версионируется рядом со сборщиками (`synology/`, `bitrix24/`).
   Минус: нужен выделенный пользователь Frappe и пара переменных окружения.
2. MCP-протокол внутри Frappe (streamable HTTP endpoint приложения). Не нужен отдельный
   процесс, но нестандартно для локальных агентов, придётся решать аутентификацию
   MCP-клиента самим (токены, CORS), и отказ FastMCP-сервера — это отказ части сайта.
3. MCP-сервер, импортирующий Frappe напрямую из bench. Быстро, но агент привязан к
   файловой системе сервера реестра — а хотимось, чтобы аналитик запускал агента
   на своей машине.

Выбран **подход 1**: дешевле всего поддерживать, не трогает инварианты, работает для
агента на любом хосте, который видит сайт Frappe.

## Как устроено

Каталог `mcp_server/` в корне репозитория (как `synology/`, `bitrix24/`, `tools/`):

- `mcp_server/client.py` — минимальный REST-клиент Frappe: `Authorization: token key:secret`,
  GET `/api/method/<dotted path>`, таймаут, понятные ошибки (текст `exc` из ответа).
- `mcp_server/server.py` — FastMCP-сервер `kartoteka`, только чтение.
- `mcp_server/requirements.txt`, `mcp_server/README.md` — установка и настройка клиентов.

Аутентификация: env `KARTOTEKA_URL`, `KARTOTEKA_API_KEY`, `KARTOTEKA_API_SECRET`
(по аналогии с `REGISTRY_URL`/`API_KEY`/`API_SECRET` у сборщиков). Пользователь Frappe —
с ролью `Access Catalog Viewer` (видит сотрудников, каталоги, контрольные списки и
отчёты по своим системам; персональные данные не получает).

## Инструменты (все read-only)

| Инструмент | Данные | Метод API |
|---|---|---|
| `whoami` | кто пользователь сервера и что видит | `bootstrap` |
| `search_people` | поиск сотрудников, флаги рисков | `people` |
| `get_person` | карточка 360°: учётки, доступы, роли, сверка, SoD | `person` |
| `get_position_profile` | должность: держатели, роли по правилам, типовой доступ | `position` |
| `list_access_roles` / `get_access_role` | каталог ролей / роль с составом и членами | `roles`, `role` |
| `list_entitlements` | каталог прав доступа | `entitlements` |
| `list_processes` / `get_process` | бизнес-процессы и роли процессов | `processes`, `process` |
| `list_reports` / `run_report` | отчёты, включая role mining и SoD | `reports_catalog`, `run_report` |
| `list_control_findings` | контрольные списки: excess/missing/sod/privileged/… | `control` |
| `search_registry` | сквозной поиск | `search` |
| `suggest_roles` | предложение ролей для сотрудника (композиция) | `person` + `position` + `roles` |

`suggest_roles` собирает за один вызов агента: текущие роли сотрудника, сверку
«положено/есть» (недостающие и лишние права с обоснованием `expected_by`), типовой
доступ его должности и каталог действующих ролей; затем считает покрытие: для каждого
«не хватает» и для типового доступа, который не покрывает ни одна текущая роль,
находит действующие роли, дающие это право. Агент на этом основании рассуждает
(«назначить существующую роль X / создать черновик через role mining»), решение
принимает человек.

## Инварианты

1. Источники — только чтение: сервер не вызывает ни одного POST-метода.
2. Права проверяет реестр: сервер — обычный пользователь Frappe с ролью читателя,
   без административных ролей; персональные данные ему API не отдаёт.
3. Секреты — только env, в коде и логах их нет; README запрещает коммитить `.env`.

## Проверка

- `ruff check mcp_server` и `ruff format --check mcp_server` (стиль репозитория: табы,
  двойные кавычки, длина строки 110).
- Установка `mcp` в venv, импорт модуля сервера и перечисление инструментов без живого
  Frappe (smoke-тест регистрации).
- Полный end-to-end против живого сайта в этом окружении невозможен (нужен доступ к
  сайту и ключ): покрытие ручное по README.

## Что оставлено за рамками (следующие итерации)
