# Заявки на доступ через смарт-процесс Битрикс24 + контроль исполнения — дизайн

Дата: 2026-11-03. Статус: подход согласован (вариант A), ожидает утверждения.

## Зачем

Реестр отвечает «что не так», но не замыкает контур «попросили → согласовали → выдали/
отозвали → проверено». Система заявок уже есть — коробочный Битрикс24 со смарт-процессом
заявок на доступ; плодить вторую не нужно. Реестр читает заявки, даёт по ним экспертизу
и контролирует, что согласованное исполнено (и что решения пересмотра «Отозвать»
исполнены тоже).

Инвариант сохраняется: в Битрикс24 реестр **не пишет** (как и сейчас, кроме отчества,
даты рождения и UUID сотрудника).

## Решения (приняты в обсуждении)

- Заявки живут в Б24 (создание, маршруты, согласование); реестр — read-only.
- Объём первого релиза: зеркало заявок + экспертиза + контроль исполнения заявок и
  отзывов пересмотра. Орфаны и JML-чек-листы — позже.
- Смарт-процесс у заказчика существующий; маппинг полей — автоугадывание с ручной
  поправкой, как у техподдержки и подбора.
- Подход A: третий `purpose` в существующем механизме `B24 Smart Process`, а не новый
  коннектор.

## Что делаем

### 1. Третий вид смарт-процесса «Заявки на доступ»

- `B24 Smart Process.purpose`: новая опция «Заявки на доступ».
- `smart_items.py`: `ACCESS_ROLES` — шаблоны автоугадывания полей по названиям (как
  `ROLES`/`HIRING_ROLES`): «кому» (сотрудник), «что» (право/роль/доступ),
  «действие» (выдать/отозвать), «основание» (текст). Пустые поля угадываются при
  сохранении процесса, поправляются вручную.
- `B24 Smart Item`: новые поля, заполняемые только для этого purpose (по образцу
  полей подбора): `access_person` (Link Person — из «кому», привязка через
  существующий резолвер), `access_what` (Data — как написано в заявке),
  `access_action` (Select: Выдать/Отозвать), `access_reason` (Data),
  `entitlement` (Link Entitlement — сопоставленное право каталога, см. п.2).
- Синк, предохранитель, Sync Log, расписание — без изменений (зеркало и так
  перестраивается целиком).

### 2. Сопоставление с каталогом прав

- Автоматически при загрузке: точное совпадение названия из заявки с названием
  Entitlement (без учёта регистра), затем — вхождение; неоднозначность не
  сопоставляется.
- Ручная привязка: поле `entitlement` правится в desk администратором; при следующей
  загрузке ручная привязка не затирается (как `person` в других коннекторах).

### 3. Раздел «Заявки» в приложении `/registry`

- Новая секция `requests` («Заявки на доступ») в `app_access.SECTIONS` + поле
  `s_requests` в профиле доступа (патч: у существующих профилей выключено; роли —
  как остальные разделы, просмотр).
- Список заявок: состояние, стадия, кто просит, кому, что, действие, основание,
  дата, ссылка на заявку в Б24 (поле `url` уже есть).
- Экспертиза по строке (видна согласующему и контролёру): что у человека уже есть по
  этому праву (есть/нет/частично), конфликт SoD (правила, где запрошенное право
  конфликтует с имеющимися у человека), владелец права из каталога, открытые дубли
  (уже есть согласованная заявка на то же).
- Все API — с `require_section("requests")` и фильтром по системам как в других
  разделах; изменения (ручная привязка entitlement) — только POST.

### 4. Контроль исполнения

- **Заявки.** На форме `B24 Smart Process` — поле «Стадия согласования» (Link
  B24 Smart Stage): заявки в этой и последующих стадиях — «ожидание исполнения».
  Проверка: для «Выдать» — право появилось у человека
  (`engine.actual_entitlements()`), для «Отозвать» — исчезло. Исполнено —
  отметка на зеркале (поле `executed_at`); не исполнено за N дней от входа в
  стадию — попадает в новый список Контроля «Заявки: не исполнено».
- **Отзывы пересмотра.** Решения «Отозвать», по которым `still_granted` жив дольше
  N дней от даты решения, — в тот же список Контроля (отдельным видом строк).
  Поле не нужно: считается на лету из даты решения и зеркала источников.
- N — константа 7 дней (моё решение; при желании позже — в настройки).
- Проверка — scheduled-задача `smart_items.scheduled_execution_check`
  (ночью, после загрузок источников; имя уникально по последним двум частям) +
  пересчёт на лету при открытии списка.
- Новый список в `app_access.CONTROLS` («requests»: «Заявки: исполнение») — попадает
  под существующие права «Контроля» и профили.
- Новое правило уведомлений «Заявки на доступ: не исполнены» в `notify.py` —
  ответственному за каталог/администратору реестра.

## Подходы

- **A (выбран):** третий purpose в существующем механизме смарт-процессов.
- **B:** отдельный коннектор заявок с нуля — дублирует отлаженную машинерию
  (зеркало, предохранитель, маппинг), отклонён.
- Контроль исполнения: «ожидание» как вычисляемое состояние (выбрано) против
  отдельного DocType задач — реестр не таск-трекер; задачи исполнителям живут в Б24.

## Решения, принятые мной (можно оспорить)

- Срок исполнения N=7 дней — константа, не настройка.
- «Согласовано» определяется стадией процесса, а не полем-галкой: стадии уже
  зеркалятся; какая именно — выбирается на форме процесса.
- Экспертиза SoD — только против текущих прав человека (не против других открытых
  заявок, кроме пометки-дубля).
- Отзывы пересмотра не создают заявок в Б24: контроль идёт в Контроле реестра и
  уведомлениях.

## Не делаем (anti-goals)

- Не пишем в Б24 (задачи, комментарии, статусы) — инвариант.
- Не создаём заявки из реестра и не согласуем в реестре — это Б24.
- Не выдаём и не отзываем доступы автоматически.
- Орфан-учётки и JML-чек-листы — отдельными шагами (JML после дизайна
  `2026-11-03-hr-events-maintenance-design.md`).

## Тесты

- Парсинг заявок нового purpose на фикстуре `fetch` (маппинг полей, автоугадывание,
  привязка `access_person`, ручной `entitlement` не затирается).
- Экспертиза: SoD-конфликт ловится, «уже есть» определяется; права доступа к API
  (403 без раздела).
- Контроль исполнения: исполнение закрывает ожидание (выдача и отзыв), просрочка
  попадает в список Контроля; отзывы пересмотра — через `still_granted` и дату
  решения.
- Правило уведомлений срабатывает только на просроченные.
- Новый раздел в профилях: `test_app_access`, workspace/навигация — существующие
  тесты.
