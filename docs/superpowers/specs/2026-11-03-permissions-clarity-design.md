# Понятная система прав — дизайн

Дата: 2026-11-03. Статус: согласовано в обсуждении, ожидает утверждения.

## Зачем

Доступ к разделам `/registry` собирается из ролей Frappe и профилей «Registry Access
Profile», где результат зависит от трёх переключателей в разных секциях формы
(раздел × системы × явный список), логика «пусто — значит всё», а отчёты выбираются по
английским внутренним именам. Показательный случай: дать чтение отчётов по общим папкам
— надо догадаться про галку «Отчёты» + галку «Общие папки» в «Системах».

Цель: администратор понимает, что даёт профиль, до сохранения; видит итог по любому
пользователю; модель не требует держать в голове двойные отрицания.

## Решения (приняты в обсуждении)

Делаем все четыре направления: резюме на форме профиля, проверка доступа по
пользователю, упрощение модели, справка.

## Что делаем

### 1. Живое резюме на форме профиля (desk)

- Новый `registry_access_profile.js`: HTML-поле «Этот профиль даёт» на форме,
  пересчитывается при любом изменении полей.
- Текст резюме строит Python-функция (новый модуль
  `access_registry/access_registry/access_summary.py`, тестируемая), whitelisted-метод
  принимает doc с формы и возвращает список строк по-русски, например:
  «Разделы: Отчёты (просмотр); Контроль (работа: Общие папки: замечания)»,
  «Системы: Общие папки», «Отчёты: Кто имеет доступ к папкам; Замечания по правам папок»
  (русские названия из `registry/reports.py CATALOG`), «Персональные данные: да».
- Важно: резюме честно показывает пересечение с «Системами» — если выбран отчёт группы,
  чья система не разрешена, строка помечается («не откроется: система не разрешена»,
  до упрощения п.3; после п.3 пометка не нужна).

### 2. Проверка доступа по пользователю

- Дорабатываем существующий экран `access_admin` в `/registry` (не новый раздел):
  у пользователя раскрывается деталь — что даёт каждый раздел (описания из профиля),
  какие отчёты доступны (русские названия), уровень и источник каждого доступа (via).
- Поиск/фильтр по имени пользователя на этом экране.

### 3. Упрощение модели

- **Явный список отчётов сильнее системного фильтра**: если в профиле заполнен
  «Только эти отчёты», перечисленные отчёты доступны независимо от галок «Системы»
  (правка `app_access.report_names`). Системы продолжают ограничивать строки данных и
  группы отчётов, когда явного списка нет.
- В дочерней таблице «Только эти отчёты» выбор ограничен отчётами каталога реестра
  (query в JS), в резюме они видны по-русски.
- Описания полей «Системы» дополнены: «влияет на группы отчётов и строки данных».
- Поведение ролей Frappe (ROLE_ACCESS) не меняется.

### 4. Справка

- `docs/access.md`: матрица «роль → что даёт», модель профиля (разделы, уровни,
  системы, списки), рецепты: «дать чтение отчётов по общим папкам», «дать техподдержке
  только её раздел», «аудитор только смотрит». Ссылка из описания DocType профиля и из
  README.

## Подходы

- Проверка по пользователю: доработка существующего `access_admin` (выбрано) против
  новой страницы — экран уже есть, администраторы туда ходят, дублировать незачем.
- Резюме: живое HTML-поле с пересчётом на клиенте (выбрано) против read-only поля,
  заполняемого при сохранении, — живое видно до сохранения, цена — один whitelisted
  вызов.

## Решения, принятые мной (можно оспорить)

- Логика резюме — на сервере (Python), а не дублируется в JS: один источник правды,
  тестируется обычными тестами.
- Семантика «явный список сильнее систем» применяется только к отчётам; для списков
  «Контроля» системы остаются фильтром строк (там это осмысленно).
- Справка — markdown в `docs/`, не вики и не отдельная страница в приложении.

## Не делаем (anti-goals)

- Не меняем модель прав DocType в админке (роли Frappe на DocType) — речь о доступе к
  приложению `/registry`.
- Не вводим новые уровни и новые сущности прав.
- Не трогаем `permissions.py` (has_permission для DocType).

## Тесты

- `access_summary`: резюме профиля — разделы, уровни, системы, отчёты по-русски,
  пометка конфликта «отчёт vs система».
- `app_access.report_names`: явный список отчётов доступен без галки системы; без
  явного списка системный фильтр работает как раньше.
- `access_admin`: деталь пользователя содержит русские названия отчётов.
