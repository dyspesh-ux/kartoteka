# Развёртывание в бою

Инструкция для установки реестра на рабочий сервер. Разработка и тестовый стенд — в
[README](../README.md#тесты-и-разработка) и [dev-setup-wsl.md](dev-setup-wsl.md).

## 1. Сервер

Реестр — обычное приложение Frappe v15. Рекомендуемый способ — Docker по схеме frappe_docker с
отдельным сервером MariaDB: [docker.md](docker.md). Другие штатные способы:

- **frappe_docker** — проще всего обновлять; в нём уже есть все процессы (web, воркеры,
  планировщик, socketio, redis);
- **bench в production-режиме** на Ubuntu 22.04/24.04:
  `sudo bench setup production <пользователь>` настраивает nginx и supervisor.

Ресурсы для организации в несколько тысяч сотрудников: 2–4 vCPU, 8 ГБ RAM, 40 ГБ диска
(основной рост — история версий и журнал синхронизаций).

Нужны процессы:

| Процесс | Зачем |
|---|---|
| web (gunicorn) | desk и приложение `/registry` |
| воркер `default`, `short` | обычные фоновые задачи |
| воркер **`long`** | загрузки ЗУП, прав 1С, AD, Битрикс24 — без него синхронизации встанут в очередь и не выполнятся |
| **планировщик** | расписание загрузок, ночной снимок прав 1С, пересчёт ролевой модели, снятие просроченных гашений |

Проверка: `bench --site <site> doctor` — планировщик включён, воркеры живы, очередь не копится.

## 2. Сайт

```bash
bench new-site registry.company.local --admin-password '<пароль>'
bench get-app https://github.com/<owner>/kartoteka.git --branch main
bench --site registry.company.local install-app access_registry
bench --site registry.company.local enable-scheduler
bench --site registry.company.local set-maintenance-mode off
```

Настройки сайта:

- **HTTPS обязателен**: в реестре персональные данные и сведения о доступах. Сертификат —
  корпоративный (`ssl_certificate`, `ssl_certificate_key` в `site_config.json`, затем
  `bench setup nginx` и перезапуск nginx) или Let's Encrypt (`bench setup lets-encrypt`).
- **Часовой пояс** — System Settings → Time Zone. От него зависят «сегодня» в статусах и
  расписание загрузок.
- `developer_mode` **выключен** (иначе правки DocType в интерфейсе попадут в файлы приложения).
- **Двухфакторная аутентификация** — System Settings → «Включить двухфакторную аутентификацию»
  (хотя бы для ролей Registry Admin и Registry Auditor).
- **Исходящая почта** (Email Account с «Использовать для исходящих» и «По умолчанию») — для
  утренней сводки и сброса паролей. Проверка: «Утренняя сводка» → «Отправить сейчас».

## 3. Пользователи

| Кто | Роль | Примечание |
|---|---|---|
| Администратор реестра | Registry Admin | подключает источники, видит всё |
| Служба безопасности, аудит | Registry Auditor | всё читает, гасит замечания, видит даты рождения |
| Владельцы ролевой модели | Access Role Manager | роли, права, исключения, гашение замечаний |
| Владельцы процессов | Process Manager | бизнес-процессы и их участники |
| Руководители (пересмотр доступа) | Access Reviewer | видят только свои задания в `/registry` |
| Сборщики и n8n | 1C Sync | технический пользователь с API-ключом, без входа в интерфейс |

Подробнее — [Кто работает с реестром](../README.md#кто-работает-с-реестром). Пароль
`Administrator` после установки смените и не используйте его для ежедневной работы.

Технические пользователи `sync-zup@access.local` и `sync-ad@access.local` создаются при установке:
от их имени загрузки пишут изменения. Входа у них нет — так и оставьте.

## 4. Сеть

Реестр **только читает** источники. Какие соединения нужны:

| Откуда → куда | Порт | Зачем |
|---|---|---|
| реестр → базы 1С (HTTP-сервисы `hr_export`, `itaccess`) | 80/443 | кадры и права 1С |
| реестр → контроллеры домена | 636 (LDAPS) или 389 | учётки и группы AD, учётка только на чтение |
| реестр → Битрикс24 (вебхук и `/local/registry/export.php`) | 443 | пользователи, структура, права |
| NAS Synology → реестр (`/api/method/access_registry.file_shares.api.upload`) | 443 | сборщик сам отправляет права папок |
| n8n → реестр (если права 1С везёт n8n) | 443 | API импорта |
| пользователи → реестр | 443 | desk и `/registry` |

Входящие соединения к реестру нужны только от пользователей, NAS и n8n; наружу в интернет
реестру ходить не нужно (кроме облачного Битрикс24, если он облачный).

## 5. Секреты

- Пароли источников (1С, учётка AD, вебхук Битрикс24, ключ скрипта выгрузки) хранятся **только в
  полях Password** и шифруются ключом `encryption_key` из `site_config.json`.
- **Сохраните `encryption_key` отдельно от бэкапов базы.** Без него восстановленная база не сможет
  расшифровать пароли источников — придётся вводить их заново.
- Ключ `REGISTRY_TOKEN` скрипта Битрикс24 и API-ключ сборщика Synology — длинные случайные строки
  (`openssl rand -hex 32`), у каждого сборщика свой пользователь и ключ.
- Реальные выгрузки (ЗУП, AD, права) в репозиторий не кладутся — только синтетика в
  `access_registry/tests/fixtures`.

## 6. Бэкапы

```bash
# ежедневно (cron или планировщик frappe_docker):
bench --site registry.company.local backup --with-files --compress
```

Храните копии вне сервера реестра, не меньше 30 дней. Раз в квартал проверяйте восстановление на
тестовом сайте: `bench --site test.local restore <файл.sql.gz>` + тот же `encryption_key`.

Что особенно ценно в бэкапе: ручные решения, которых нет в источниках, — привязки учёток к
сотрудникам, склейки, ролевая модель, исключения, **журнал гашений**, результаты пересмотров.

## 7. Обновление

Рабочая ветка — `main`: в неё попадают изменения, прошедшие CI (тесты на чистой установке).

```bash
cd frappe-bench/apps/access_registry && git pull origin main && cd ../..
bench --site registry.company.local backup
bench --site registry.company.local migrate
bench restart            # frappe_docker: пересоздать контейнеры с новым образом
```

`migrate` обновляет DocType, отчёты и рабочие столы раздела «Access Registry» (они часть
приложения и восстанавливаются из репозитория). Приложение `/registry` сборщик не использует;
для desk есть один скрипт (`public/js/registry_desk.js`), поэтому после обновления на bench
выполните `bench build --app access_registry` (в frappe_docker он уже в новом образе).

## 8. Первый запуск по порядку

1. **Базы ЗУП** → «Проверить подключение» → «Загрузить». Разобрать кандидатов на склейку.
2. **Домен AD** → загрузить. Проверить «Учётки без сотрудника»; при желании проставить
   `employeeNumber` скриптом из отчёта «AD employeeNumber».
3. **Права 1С** по всем базам (снимок из `ВыгрузкаПрав_ИТ` или через n8n).
4. **Битрикс24**: вебхук и скрипт выгрузки, загрузка; запись в профили включать после проверки
   привязок.
5. **Synology**: файловый сервер, сборщик с `--dry-run`, загрузка из файла, затем планировщик DSM.
6. **Ролевая модель**: «Подбор ролей» → черновики → утвердить; исключения; правила SoD.
7. Разобрать «Контроль»: закрыть реальные проблемы, остальное погасить с комментарием.
8. Включить **утреннюю сводку** и выбрать получателей: с этого дня новое приходит на почту само.

## 9. Эксплуатация

- **Журнал синхронизаций** (Sync Log) — каждый запуск с результатом; «Остановлен
  предохранителем» значит, что источник отдал подозрительно мало данных и реестр ничего не
  менял. Хранится 180 дней (Log Settings).
- **Error Log** Frappe — ошибки фоновых задач.
- Главная `/registry` → «Источники»: у каждого источника дата последней успешной загрузки. Если
  она старше суток — смотрите журнал и воркер `long`.
- Очередь: `bench --site <site> show-pending-jobs`.
