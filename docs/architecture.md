# Архитектура: слои реестра

Реестр отвечает на вопрос «кто есть кто и у кого какой доступ». Данные собираются из нескольких
систем. Каждая система — отдельный слой, и каждый следующий слой опирается на предыдущие.
Система **только читает** 1С, AD и Synology. В Битрикс24 она дописывает отчество, дату рождения и UUID
сотрудника, если это включено.

```
 1. Кадры (базы ЗУП)          источник правды: сотрудники, подразделения, организации
        │  Person (собственный UUID)
        ▼
 2. Active Directory          учётки и группы → привязаны к сотруднику (employeeNumber = UUID)
        │
        ▼
 3. Пользователи 1С           ЗУП, Бухгалтерия и другие базы → привязаны к сотруднику и учётке AD
        │
        ▼
 4. Битрикс24                 привязан к сотруднику (через AD), обогащается данными из ЗУП
        │
        ▼
 4a. Общие папки Synology     права шар и папок → учётки и группы AD (с вложенностью) → сотрудники
        │
        ▼
 5. Свои процессы и роли      бизнес-роли, «положено / есть», заявки → к сотрудникам
```

## Общие понятия

| Понятие | DocType | Роль |
|---|---|---|
| База 1С | `Info Base` | Любая информационная база 1С. **Конфигурация** решает, что из неё берётся: из **ЗУП** — кадры (слой 1), а также пользователи и права (слой 3); из **Бухгалтерии** и других — только пользователи и права. Код базы (`ZUP1`, `BP1`) входит в ключи всех её записей и не меняется |
| Сотрудник | `Person` | Человек, склеенный по всем базам ЗУП. Его UUID постоянный и не меняется даже при склейке: он уйдёт в AD `employeeNumber` и станет общим ключом всех слоёв |
| Журнал синхронизаций | `Sync Log` | Каждый запуск любой загрузки: кадры, права 1С, журнал 1С, AD. Позже — Bitrix24 |
| Настройки | `Access Registry Settings` | Общие пороги предохранителя, таймауты, пользователь синхронизации |

## Слой 1. Кадры (базы ЗУП) — сделано

Источник правды о сотрудниках, подразделениях и организациях. Баз ЗУП может быть несколько.
Загружаются только из баз с конфигурацией ЗУП, через расширение `HR_Export_API`.

- `Person`: склейка по GUID физлица, ФИО и дате рождения. Спорные пары — `Person Merge Candidate`;
- `Employment`, `HR Department` (дерево), `HR Organization`, `Legal Entity`, `HR Position`, `HR Absence`;
- `HR Event`: приём, увольнение, перевод и другие события — вход для чек-листов слоя 5.

## Слой 2. Active Directory — сделано

Frappe сам читает каталог по LDAP/LDAPS (библиотека `ldap3`, уже есть в зависимостях Frappe),
**только чтением**: bind учёткой без прав на запись, `read_only=True`. Доменов может быть несколько.

- `AD Domain` — домен: сервер(ы) LDAP, Base DN, учётка для чтения (пароль — поле Password),
  фильтры и OU поиска. Кнопки «Проверить подключение» и «Загрузить», по расписанию — раз в час;
- `AD Account` — учётка: логин, UPN, включена/заблокирована, пароль не истекает, последний вход,
  OU, должность и отдел из AD, руководитель, `employeeNumber`, прямые группы (`AD Account Group`);
- `AD Group` — группа: область действия, безопасность/рассылка, число прямых участников,
  ответственный из AD (`managedBy`) и ручные поля «Под контролем», «Владелец», «Назначение»;
  группы, в которые она вложена (`parent_groups`, из `memberOf`). Действующие группы учётки —
  прямые плюс все, в которые они вложены (`active_directory/groups.py`); по ним считаются и сверка
  ролевой модели, и доступ к общим папкам.

Ключ записей — `<код домена>:<objectGUID>`: переименование и перенос между OU не создают новых
записей. Сохранение только при реальных изменениях (хеш), история — в Versions. Последний вход и
блокировка меняются постоянно: они хранятся, но не создают версий. Пропавшие учётки и группы
помечаются «Нет в AD». Предохранитель общий с остальными загрузками.

**Привязка учётки к сотруднику** (`AD Account.person`):

1. **Вручную** (`manual_person`) — главнее всего.
2. **employeeNumber** — если в нём UUID сотрудника реестра.
3. **ФИО** — `displayName` (или фамилия, имя, отчество), тем же нормализованным сравнением, что и
   для 1С.

Реестр в AD не пишет. Отчёт «AD employeeNumber» показывает учётки, где `employeeNumber` не равен
UUID сотрудника, и по кнопке формирует скрипт PowerShell: администратор проверяет его и сам
запускает с ключом `-Apply`. После этого привязка по employeeNumber не зависит от ФИО.

Отчёты: учётка включена у неработающего, учётки без сотрудника, давно не входили, пароль не
истекает, участники группы, учётка AD отключена, а вход в 1С по ней есть.

## Слой 3. Пользователи 1С — сделано для любых баз

Расширение `ВыгрузкаПрав_ИТ` (`onec/ITAccess.bsl`) ставится в каждую базу: ЗУП, Бухгалтерию и
другие. Загружаются:
- `IB User` — пользователи 1С и пользователи ИБ без карточки;
- `IB Access Profile` — профили доступа;
- `IB Audit Event` — журнал изменений прав.

**Привязка пользователя 1С к сотруднику** (`IB User.person`, способ — в `person_link_method`):

1. **Вручную** (`manual_person`) — всегда главнее, загрузка это поле не меняет.
2. **GUID физлица (ЗУП)** — только в базах ЗУП: физлицо из карточки пользователя ищется в кадровых
   данных той же базы.
3. **Учётка AD** — в любой базе: «Пользователь ОС» 1С (`\\CORP\ivanov`) → домен по NetBIOS-имени
   `AD Domain` и логин → `AD Account` → её сотрудник. Ссылка на учётку сохраняется в
   `IB User.ad_account` всегда, даже если сотрудник найден по GUID. После каждой загрузки AD
   пользователи 1С перепривязываются сразу, не дожидаясь следующего снимка прав.
4. **ФИО** — в любой базе: ФИО физлица из карточки, а если его нет — имя пользователя. Сравнивается
   нормализованно: регистр, ё/е, латинские буквы-двойники. Если однофамильцев несколько, выбирается
   единственный работающий, иначе связи нет.

Почему связь не найдена, видно в поле «Почему не найден» и в отчёте «Не привязаны к сотруднику».
Все учётные записи сотрудника во всех базах видны в его карточке, в разделе «Учётные записи».

## Слой 4. Битрикс24 — сделано

Frappe читает портал через REST (входящий вебхук, `bitrix24/client.py`: паузы между запросами,
повтор при лимитах, пакетные запросы по 50 команд, постраничное чтение) и, для коробки, через скрипт
выгрузки прав `bitrix24/registry_export.php` (роли CRM и смарт-процессы, права на папки общих
дисков, группы пользователей, логины, график отсутствий).

- `B24 User` привязывается к сотруднику: вручную → UUID в пользовательском поле → учётка AD (логин
  или почта) → ФИО → фамилия и имя (если отчества в Битрикс24 нет);
- `B24 Department` сопоставляется с `HR Department` по названию (с учётом родителя) или вручную;
- `B24 Access Grant` — права с кодом доступа; «кому» раскрывается до людей (`bitrix24/access.py`);
- обогащение из ЗУП: после загрузки реестр пишет в профили отчество, дату рождения и UUID сотрудника
  (если включено; журнал `B24 Write Log`, предел изменений за загрузку). Это единственная запись
  реестра во внешние системы.

## Общие папки Synology — сделано

Push-модель: на NAS по расписанию работает `synology/registry_collect.sh` (только чтение,
`synoshare` и `synoacltool`) и POST-ом отправляет сырой текст в `file_shares.api.upload`
(роль 1C Sync). Парсер — `file_shares/synology.py`, загрузка — `file_shares/sync.py` (одна транзакция,
предохранитель, пропавшие папки помечаются), итоговый доступ — `file_shares/access.py`.

- `File Server` — NAS, `File Share` — общая папка с правами DSM, `Folder ACL` — папка, права которой
  отличаются от родительской (ключ `<сервер>:<папка>:<md5 пути>`), с историей версий.
- Сборщик записывает только места, где права меняются. `STOP_ON_SAME=1` ускоряет обход, но не видит
  особых прав внутри папок «как у родителя» (по умолчанию 1, раз в неделю — полный обход с 0).
- Доступ = min(права DSM, ACL); запрет для учётки или любой её группы закрывает доступ.

## Слой 5. Ролевая модель и бизнес-процессы — сделано

Должность — не роль, а главный признак, по которому сотрудник получает роли. Подробно:
[roles-and-processes.md](roles-and-processes.md).

- `Entitlement` — право доступа в системе (профиль 1С, группа AD, группа или право Битрикс24);
- `Access Role` — набор прав: базовая, должностная (правила по трудоустройствам), дополнительная
  (назначение на срок); `Access Exception` — согласованное лишнее; `SoD Rule` — несовместимые права;
- `Business Process` (дерево), `Process Role` (RACI, нужные права), `Process Participant`;
- `access_roles/engine.py` — «положено» (роли и роли процессов) против «есть» (зеркала 1С, AD,
  Битрикс24), конфликты полномочий, подбор ролей по уже выданным доступам.

Сделано также: пересмотр доступа руководителями (`access_roles/review.py`) и гашение замечаний с
журналом (`access_roles/suppression.py`), утренняя сводка по почте (`access_roles/digest.py`).
Следующее: чек-листы по кадровым событиям с исполнителями и сроками, заявки на доступ.

## Приложение для пользователей

`/registry` (`www/registry.*`, API `registry/api.py`) — одна страница без сборки и внешних
библиотек: обзор рисков, сотрудники и карточка 360°, контрольные списки с выгрузкой в CSV,
каталоги прав, ролей и процессов. Каждый метод API сам проверяет роль пользователя
(`permissions.py`), даты рождения получают только администраторы и аудиторы.

## Как добавить новый источник

1. Справочник источника — отдельный DocType, по аналогии с `Info Base`. Для 1С это `Info Base`
   с нужной конфигурацией.
2. Записи источника именуются `<код источника>:<идентификатор>` и хранят хеш исходных данных:
   сохранение только при реальных изменениях, повторная загрузка не создаёт версий.
3. Пропавшие из источника записи не удаляются, а помечаются.
4. Каждый запуск пишется в `Sync Log` со своим видом.
5. Привязка к сотруднику — поле `person` со способом привязки и ручным переопределением.
6. Ярлыки и отчёты — в разделе Access Registry (`access_registry/access_registry/workspace/`).
