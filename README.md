# Access Registry

Реестр «кто есть кто и у кого какой доступ» на Frappe Framework v15.

**Этап 1. Зеркало кадровых данных 1С:ЗУП КОРП.** Приложение читает HTTP-сервис расширения
`HR_Export_API` в каждой базе ЗУП и строит в Frappe сводную картину: юрлица, организации, дерево
подразделений, должности, люди (склеенные по всем базам), трудоустройства, отсутствия и кадровые
события. Система **только читает** источники: никаких записей в ЗУП, AD или Bitrix24.

## Установка

Нужен bench с Frappe v15 (обычный или [frappe_docker](https://github.com/frappe/frappe_docker)).
Дополнительных Python-зависимостей нет.

```bash
cd frappe-bench
bench get-app https://github.com/<owner>/<repo>.git   # или путь к локальному клону
bench --site <site> install-app access_registry
bench --site <site> migrate
```

Что делает установка:

- создаёт DocType модуля **Access Registry** (все они хранятся JSON-файлами в приложении);
- создаёт корень дерева подразделений «Все организации» (`ROOT`);
- создаёт технических пользователей `sync-zup@access.local` и `sync-ad@access.local`, от имени
  которых синк записывает изменения. Входа у них нет: нет ни пароля, ни ролей.

Для работы синхронизации нужны:

- **планировщик** — `bench --site <site> enable-scheduler`;
- **воркер очереди `long`**. В frappe_docker это сервис `queue-long`; на обычном bench —
  `bench worker --queue long`, это уже есть в Procfile/supervisor;
- **часовой пояс сайта** (System Settings → Time Zone). От него зависят «сегодня» для статусов и
  окно запроса отсутствий. Расписание cron тоже считается по нему.

Для разработки DocType включите developer mode (`bench --site <site> set-config developer_mode 1`),
чтобы правки DocType сохранялись в JSON-файлы приложения.

## Настройка источника

1. **Access Registry Settings** (Single). Все поля необязательны: без сохранения работают значения
   по умолчанию.

   | Поле | По умолчанию | Смысл |
   |---|---|---|
   | Допустимое сокращение выгрузки, % | 10 | предохранитель, см. ниже |
   | Минимум записей для предохранителя | 20 | предохранитель включается, когда в реестре столько актуальных записей источника |
   | Пользователь синхронизации | `sync-zup@access.local` | автор изменений в истории версий |
   | Ключевые слова должностей руководителей | руководитель, начальник, директор, заведующий, главный, заместитель | по одному на строку, по приоритету |
   | Отсутствия: дней назад / вперёд | 30 / 180 | окно запроса `/absences` |
   | Таймаут HTTP-запроса, сек | 300 | |
   | Таймаут фоновой задачи синка, сек | 7200 | также максимальное ожидание очереди, пока синхронизируется другой источник |

2. **HR Source** — по одному на базу ЗУП:
   - **Код источника** — короткий постоянный код (`ZUP1`, `ZUP2`: латиница, цифры, `_`, `-`).
     Код входит в ключи всех записей источника (`ZUP1:<GUID>`), поэтому после создания его
     изменить нельзя. Не используйте имя базы из URL: база может переехать, а код останется.
   - **Базовый URL** — адрес HTTP-сервиса без имени эндпоинта, например
     `http://1c.example.local/zup/hs/hr_export`. Приложение обращается к
     `<URL>/meta`, `/organizations`, `/departments`, `/employees`, `/absences?from=…&to=…`.
   - **Пользователь** (`svc_hr_export`) и **Пароль**. Пароль хранится в зашифрованном поле
     Password, не в коде и не в конфигурации.
   - **Проверять сертификат HTTPS** — пока сервис работает по HTTP, флаг ни на что не влияет. После
     перехода на HTTPS с сертификатом внутреннего УЦ добавьте корневой сертификат в системное
     хранилище контейнера, а не выключайте проверку.
   - **Включён** — только включённые источники синхронизирует планировщик.

## Первая загрузка

1. Создайте HR Source и нажмите **«Синхронизировать сейчас»**. Задача встанет в очередь `long`.
   Повторное нажатие, пока задача в очереди или выполняется, новую задачу не создаёт.
2. Откройте **Sync Log** (кнопка «Журнал синхронизаций» в форме источника). Запуск со статусом
   «Успех» и флагом «Первая загрузка» означает, что зеркало построено.
3. Первая загрузка идёт **без кадровых событий**: иначе каждый сотрудник дал бы «Приём». Счётчик
   `HR Event → suppressed_first_load` показывает, сколько событий подавлено.
4. Если баз несколько, загружайте их по очереди. Синки разных источников и так выполняются
   последовательно: пока идёт один, следующий ждёт его окончания.
5. После загрузки:
   - разберите **Person Merge Candidate** (следующий раздел);
   - посмотрите людей с флагом **«Только совместительство»**. Это люди с активными
     трудоустройствами, но без основного места работы (в том числе внешние совместители). Их
     разбирают вручную;
   - просмотрите дерево подразделений (**HR Department → Tree**): у каждого подразделения поле
     **«Кандидат по должности»** и кнопка **«Принять кандидата»**;
   - заполните **Директор** у юрлиц (Legal Entity).

Дальше планировщик запускает синк сам: каждые 30 минут с 7:00 до 21:00 и раз в час ночью.

Ориентир по скорости на синтетических данных (5000 сотрудников, 400 подразделений): первая
загрузка около 3 минут, повторный синк без изменений около 15 секунд, новых версий 0.

## Разбор кандидатов на склейку

Один человек в разных базах ЗУП имеет разные GUID физлица. Реестр сопоставляет людей так:

1. Физлицо источника уже известно (есть строка в **Физлица в источниках**) — это он.
2. Иначе ищется Person с тем же ключом «фамилия | имя | отчество | дата рождения». Ключ
   нормализуется: регистр, ё→е, лишние пробелы, латинские буквы-двойники → кириллица. Если такой
   человек ровно один и у него ещё нет физлица из этой же базы, новое физлицо добавляется к нему.
3. Иначе создаётся новый Person, и при похожих совпадениях появляется **Person Merge Candidate**:
   - «Совпадают ФИО и дата рождения» — например, два физлица-дубля в одной базе;
   - «Совпадают имя, отчество и дата рождения (смена фамилии?)».

Без даты рождения или без имени люди автоматически не сопоставляются.

В форме кандидата:

- **«Склеить B в A»**. Физлица источников B переходят к A. Все ссылки на B в любых DocType
  переводятся на A: трудоустройства, события, отсутствия, руководители подразделений, директора
  юрлиц, другие кандидаты. B удаляется (копия остаётся в Deleted Document), в A пишется
  комментарий. **UUID человека A не меняется**: он потом уйдёт в AD `employeeNumber`.
- **«Это разные люди»**. Пара закрывается и больше не предлагается.

## Как читать Sync Log

Каждый запуск синхронизации одного источника — одна запись Sync Log.

| Поле | Что там |
|---|---|
| Статус | **В процессе**, **Успех**, **Остановлен предохранителем**, **Ошибка** |
| Первая загрузка | запуск шёл без событий |
| Счётчики (`stats`) | JSON по сущностям: `created`, `updated`, `unchanged`, `missing` (пропали из выгрузки), `moved` (подразделение перенесено), `head_updated`, `cancelled` (отменённые отсутствия), `status_updated` (пересчитан статус человека), `linked_by_match_key` (физлицо привязано к человеку из другой базы), события по типам, `guard` (сколько записей в выгрузке и в реестре), `warnings` |
| Предупреждения и ошибки | предупреждения построчно, при ошибке — полный traceback |
| Ответ /meta | снимок регистра состояний и видов состояний на момент запуска |

Журналы хранятся 180 дней, срок меняется в стандартных **Log Settings** Frappe.

Статус и время последнего запуска видны и в форме HR Source («Статус последнего запуска»,
«Последний успешный синк»).

Весь синк источника выполняется **одной транзакцией**. При ошибке или срабатывании
предохранителя всё откатывается: в реестре не меняется ничего, кроме записи Sync Log. Счётчики
такого запуска показывают, что синк успел сделать до остановки (в `stats` есть пометка `_результат`).

Типичные предупреждения:

- вид состояния с категорией «Неизвестно»/«Отсутствует» в `/meta` — в ЗУП есть вид состояния,
  которому расширение не сопоставило категорию. Решения по нему могут быть неверными, стоит
  доработать сопоставление в расширении;
- родитель подразделения не найден в выгрузке — узел повешен на организацию;
- руководитель подразделения (физлицо …) не найден среди сотрудников;
- у организации нет ИНН — юрлицо не назначено;
- отсутствия сотрудника, которого нет среди трудоустройств.

### Предохранитель

Если актуальных (`Нет в выгрузке = 0`) трудоустройств или подразделений источника в реестре не
меньше **минимума записей**, а в выгрузке их меньше, чем `актуальных × (1 − порог/100)`, синк
останавливается без изменений. Обычная причина — сбой или неполная выгрузка на стороне 1С.
Если сокращение ожидаемое (массовое увольнение, чистка справочника):

1. временно поднимите «Допустимое сокращение выгрузки, %» в Access Registry Settings. Нужное
   значение подсказывает текст в Sync Log;
2. нажмите «Синхронизировать сейчас» у источника;
3. верните прежнее значение.

## Как это работает

### Модель данных

| DocType | Что | Имя записи |
|---|---|---|
| Access Registry Settings | настройки (Single) | — |
| HR Source | база ЗУП | код источника |
| Legal Entity | сводное юрлицо по всем базам; `director` заполняется вручную | `ИНН-КПП` или `ИНН` |
| HR Organization | организация базы | `<код>:<GUID>` |
| HR Department | дерево: «Все организации» → организации → подразделения | `ROOT`, `<код>:org:<GUID>`, `<код>:<GUID>` |
| HR Position | должность (из `/employees`) | `<код>:<GUID>` |
| Person | человек по всем базам; дочерняя таблица Person Source ID | собственный UUID4 |
| Employment | трудоустройство (элемент «Сотрудники») | `<код>:<GUID>` |
| HR Absence | отсутствие из `/absences` | `<код>:<СотрудникGUID>:<Код>:<ДатаНачала>` |
| HR Event | кадровое событие; флаг «Обработано» ставят люди | `HRE-…` |
| Person Merge Candidate | спорная пара людей | `PMC-…` |
| Sync Log | журнал запусков | `SYNC-…` |

Правила:

- поля из источника доступны только для чтения, их перезаписывает синк. Ручные поля синк не
  трогает никогда: `manual_head`, `director`, `processed`;
- запись сохраняется, только если значения реально изменились. Поэтому повторный синк без
  изменений в ЗУП не создаёт ни одной версии, а `modified` остаётся осмысленным;
- записи не удаляются: пропавшие из выгрузки получают флаг **«Нет в выгрузке»**;
- у всех основных DocType включён Track Changes. Изменения синка в истории записаны от
  пользователя синка;
- дата рождения человека (и ключи сопоставления, в которых она есть) лежит на permlevel 1, её видит
  только System Manager. Для интеграций с другими системами дайте API-пользователю роль с
  доступом к permlevel 1 у Person.

### Статусы

**Трудоустройство** (по датам на «сегодня»; дата увольнения в 1С — последний рабочий день):
нет даты приёма или она в будущем → «Не принят»; дата увольнения прошла → «Уволен»; дата
увольнения сегодня или позже → «Увольняется»; иначе «Работает»; пропало из выгрузки → «Нет в
выгрузке». `Состояние` из ЗУП хранится справочно в поле «Состояние в ЗУП».

**Человек** (по трудоустройствам во всех базах):

- `status` — «Работает», если хоть одно трудоустройство «Работает»/«Увольняется»; иначе «Не
  принят», если такое есть; «Нет в выгрузке», если все такие; иначе «Уволен»;
- `presence` — «Длительное отсутствие», если все активные трудоустройства в категории
  `ОтпускПоУходу` и `ФактическиРаботает = false`; иначе «На месте». Отпуск, больничный и
  командировка на присутствие не влияют;
- «Только совместительство» — активные трудоустройства есть, но ни одно не основное место работы.

### Кадровые события

Приём, Увольнение, Предстоящее увольнение, Перевод (в подробностях «было → стало»), Уход в отпуск
по уходу и Выход из него, Пропал из выгрузки, Вернулся в выгрузку. События создаются при сравнении
с предыдущим состоянием. При первой загрузке источника событий нет. Отсутствия событий не
порождают, кроме смены присутствия.

### Руководители подразделений

- `zup_head` — из `РуководительФизЛицоGUID`.
- `manual_head` — вручную.
- `head` — итог: ЗУП важнее ручного, источник показан в `head_source`.
- `head_conflict` — ЗУП и ручное заполнены и различаются.
- `head_candidate` — подбирается, если нет ни ЗУП, ни ручного: активный сотрудник подразделения,
  чья должность начинается с первого подходящего ключевого слова; основное место работы важнее
  совместительства. Автоматически кандидат не применяется: для этого есть кнопка «Принять
  кандидата».

## Тесты и разработка

```bash
bench --site <site> set-config allow_tests true
bench --site <site> run-tests --app access_registry
```

Запускайте тесты только на dev- или тестовом сайте: перед каждым тестом они очищают таблицы
модуля (в транзакции, которая потом откатывается).

Тесты (`access_registry/tests/test_zup_sync.py`) подменяют HTTP функцией, которая отдаёт
синтетические JSON из `access_registry/tests/fixtures/zup1` и `zup2` в формате эндпоинтов.
Покрыты все сценарии ТЗ: первая загрузка, повторный синк без версий, перевод, увольнение,
карточка без приёма, совместители, человек в двух базах, смена фамилии и склейка,
предохранитель, пропажа из выгрузки, дерево и циклы, руководители, отпуск по уходу, отменённые
отсутствия, латиница в фамилии, откат при ошибке. CI (`.github/workflows/ci.yml`) ставит
приложение на чистый сайт и гоняет тесты при каждом push.

Инструменты для ручной проверки без ЗУП:

```bash
# Сгенерировать большой синтетический набор
python3 tools/generate_synthetic.py --out /tmp/zup_big --employees 5000 --departments 400
# Поднять заглушку HR_Export_API (basic auth)
python3 tools/mock_hr_export.py --dir /tmp/zup_big --port 8765 --user svc_hr_export --password secret
# HR Source: URL http://127.0.0.1:8765/hs/hr_export, пользователь svc_hr_export, пароль secret
```

**Персональные данные.** В выгрузках ЗУП есть ФИО и даты рождения (152-ФЗ). Реальные выгрузки не
кладите в репозиторий: для тестов и примеров — только синтетические данные.

## Проверка на реальной базе

1. Подключите источник, выполните первую загрузку и проверьте Sync Log: статус «Успех», разумные
   предупреждения.
2. Сверьте число людей «Работает» по каждой организации с ЗУП, например отчётом по Employment
   (статус «Работает»/«Увольняется», группировка по организации) и по Person.
3. Запустите синк ещё раз без изменений в ЗУП: в `stats` только `unchanged`, в Version нет новых
   записей по DocType модуля.
4. Проверьте, что имена эндпоинтов в расширении совпадают с ожидаемыми: `/organizations`,
   `/departments`, `/employees`, `/absences`, `/meta`. Ключ GUID принимается как `ОрганизацияGUID`/
   `ПодразделениеGUID` или `GUID`.
