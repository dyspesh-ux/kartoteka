# Access Registry

Реестр «кто есть кто и у кого какой доступ» на Frappe Framework v15.

Реестр собирается слоями ([docs/architecture.md](docs/architecture.md)):

1. **Кадры из баз ЗУП** — источник правды о сотрудниках, подразделениях и организациях
   (расширение `HR_Export_API`). Баз ЗУП может быть несколько. **Сделано.**
2. **Active Directory** — учётки, группы и прямое членство, привязанные к сотрудникам (чтение по
   LDAP). **Сделано.**
3. **Пользователи 1С** любых баз (ЗУП, Бухгалтерия, другие) — профили, организации, роли в обход
   профилей, журнал изменений прав (расширение `ВыгрузкаПрав_ИТ`); привязаны к сотрудникам и к
   учёткам AD. **Сделано.**
4. **Битрикс24** — пользователи, структура, группы и проекты, отсутствия, доступ к разделам
   (CRM, смарт-процессы, общие диски); сверка с кадрами; отчество, дата рождения и UUID сотрудника
   дописываются в профили. **Сделано.**
5. **Общие папки Synology** — права общих папок и Windows ACL подпапок (только там, где права
   меняются), кто реально имеет доступ с учётом вложенных групп AD, замечания. **Сделано.**
6. **Ролевая модель и бизнес-процессы** — права доступа, роли по должностям, исключения,
   конфликты полномочий, сверка «положено / есть»; каталог процессов, роли RACI и участники.
   **Сделано.** Почему должность — не роль: [docs/roles-and-processes.md](docs/roles-and-processes.md).

Для ежедневной работы — **приложение реестра** `/registry` для службы безопасности, ИБ и контролёров
прав (см. [Приложение реестра](#приложение-реестра)). Оформление — спокойное: зелёный акцент и оттенки серого, без красного; серьёзные проблемы
выделены тёмно-серыми плашками (`access_registry/www/registry.css`, блок `:root`). Шрифт Century
Gothic берётся установленный на компьютере (в приложение не входит из-за лицензии), без него —
похожий системный.

Система **только читает** 1С, AD и Synology. В Битрикс24 она пишет только отчество, дату рождения и UUID
сотрудника, и только если это включено в настройках портала.

## Установка

Нужен bench с Frappe v15 (обычный или [frappe_docker](https://github.com/frappe/frappe_docker)).
Дополнительных Python-зависимостей нет.

```bash
cd frappe-bench
bench get-app https://github.com/<owner>/<repo>.git --branch main   # или путь к локальному клону
bench --site <site> install-app access_registry
bench --site <site> migrate
```

Что делает установка:

- создаёт DocType модуля **Access Registry** (все они хранятся JSON-файлами в приложении);
- создаёт корень дерева подразделений «Все организации» (`ROOT`);
- создаёт роли пользователей реестра (см. [Кто работает с реестром](#кто-работает-с-реестром));
- создаёт технических пользователей `sync-zup@access.local` и `sync-ad@access.local`, от имени
  которых синк записывает изменения. Входа у них нет: нет ни пароля, ни ролей.

Для работы синхронизации нужны:

- **планировщик** — `bench --site <site> enable-scheduler`;
- **воркер очереди `long`**. В frappe_docker это сервис `queue-long`; на обычном bench —
  `bench worker --queue long`, это уже есть в Procfile/supervisor;
- **часовой пояс сайта** (System Settings → Time Zone). От него зависят «сегодня» для статусов и
  окно запроса отсутствий. Расписание cron тоже считается по нему.

Для разработки DocType включите developer mode (`bench --site <site> set-config developer_mode 1`),
чтобы правки DocType сохранялись в JSON-файлы приложения.

## Развёртывание в бою

**В Docker** (рекомендуется; сервер приложения и отдельный сервер MariaDB) — пошагово в
[docs/docker.md](docs/docker.md), файлы — в [`deploy/docker/`](deploy/docker): сборка образа по
рекомендациям frappe_docker, compose с внешней базой, HTTPS с корпоративным сертификатом, бэкапы,
обновление.

Общие требования к бою — в [docs/deployment.md](docs/deployment.md): сервер и процессы (воркер `long` и
планировщик обязательны), HTTPS и двухфакторная аутентификация, пользователи и роли, какие сетевые
доступы нужны (реестр только читает источники; NAS и n8n сами присылают данные), хранение
паролей и `encryption_key`, бэкапы и проверка восстановления, обновление, порядок первого запуска
и за чем следить в эксплуатации.

**Ветки.** `main` — рабочая: ставится в бой, изменения в неё попадают после зелёного CI (установка
на чистый сайт и все тесты, `.github/workflows/ci.yml`). Разработка — в отдельных ветках с
последующим слиянием в `main`.

## Базы 1С и настройки

1. **Access Registry Settings** (Single). Все поля необязательны: без сохранения работают значения
   по умолчанию.

   | Поле | По умолчанию | Смысл |
   |---|---|---|
   | Допустимое сокращение выгрузки, % | 10 | предохранитель, см. ниже |
   | Минимум записей для предохранителя | 20 | предохранитель включается, когда в реестре столько актуальных записей источника |
   | Пользователь синхронизации | `sync-zup@access.local` | автор изменений в истории версий |
   | Ключевые слова должностей руководителей | руководитель, начальник, директор, заведующий, главный, заместитель | по одному на строку, по приоритету |
   | Отсутствия: дней назад / вперёд | 30 / 180 | окно запроса `/absences` |
   | Таймаут HTTP-запроса, сек | 300 | |
   | Таймаут фоновой задачи синка, сек | 7200 | также максимальное ожидание очереди, пока синхронизируется другой источник |

2. **Базы 1С** (`Info Base`) — по одной записи на каждую информационную базу:
   - **Код базы** — короткий постоянный код (`ZUP1`, `ZUP2`, `BP1`: латиница, цифры, `_`, `-`).
     Код входит в ключи всех записей базы (`ZUP1:<GUID>`), поэтому после создания его изменить
     нельзя. Не используйте имя базы из URL: база может переехать, а код останется.
   - **Конфигурация** — **ЗУП** (источник кадров, плюс пользователи и права), **Бухгалтерия** или
     **Другая** (только пользователи и права).
   - Секция **«Кадровые данные»** (только для ЗУП): URL сервиса `HR_Export_API`, например
     `http://1c.example.local/zup/hs/hr_export`. Приложение обращается к `<URL>/meta`,
     `/organizations`, `/departments`, `/employees`, `/absences?from=…&to=…`. Пользователь
     `svc_hr_export` и пароль.
   - Секция **«Пользователи и права»** (любая база): см. [Пользователи 1С и права](#пользователи-1с-и-права).
   - Пароли хранятся в зашифрованных полях Password, не в коде и не в конфигурации.
   - **Проверять сертификат HTTPS** — пока сервисы работают по HTTP, флаг ни на что не влияет. После
     перехода на HTTPS с сертификатом внутреннего УЦ добавьте корневой сертификат в системное
     хранилище контейнера, а не выключайте проверку.
   - **Включена** — только включённые базы загружаются по расписанию.

   До версии с Бухгалтерией справочник назывался HR Source; `migrate` переименовывает его в
   Info Base с сохранением данных и паролей.

## Первая загрузка

Всё, что нужно для работы с ЗУП, собрано в разделе **«Access Registry»** в боковой панели (см.
[следующий раздел](#раздел-access-registry)).

1. Создайте базу ЗУП («Access Registry» → «Базы 1С») и нажмите **«Загрузить» → «Синхронизировать кадры»**. Задача встанет в очередь `long`.
   Повторное нажатие, пока задача в очереди или выполняется, новую задачу не создаёт.
2. Откройте **Sync Log** («Открыть» → «Журнал синхронизаций» в форме базы). Запуск со статусом
   «Успех» и флагом «Первая загрузка» означает, что зеркало построено.
3. Первая загрузка идёт **без кадровых событий**: иначе каждый сотрудник дал бы «Приём». Счётчик
   `HR Event → suppressed_first_load` показывает, сколько событий подавлено.
4. Если баз несколько, загружайте их по очереди. Синки разных источников и так выполняются
   последовательно: пока идёт один, следующий ждёт его окончания.
5. После загрузки:
   - разберите **Person Merge Candidate** (см. [разбор кандидатов](#разбор-кандидатов-на-склейку));
   - посмотрите людей с флагом **«Только совместительство»**. Это люди с активными
     трудоустройствами, но без основного места работы (в том числе внешние совместители). Их
     разбирают вручную;
   - просмотрите дерево подразделений (**HR Department → Tree**): у каждого подразделения поле
     **«Кандидат по должности»** и кнопка **«Принять кандидата»**;
   - заполните **Директор** у юрлиц (Legal Entity).

Дальше планировщик запускает синк сам: каждые 30 минут с 7:00 до 21:00 и раз в час ночью.

Ориентир по скорости на синтетических данных (5000 сотрудников, 400 подразделений): первая
загрузка около 3 минут, повторный синк без изменений около 15 секунд, новых версий 0.

## Приложение реестра

Адрес `/registry` (ссылка — первым ярлыком раздела «Access Registry»). Отдельное приложение для тех,
кто контролирует доступ, а не настраивает систему: без меню админки, светлая и тёмная тема, работает
на телефоне. Вход — через корпоративный SSO ([docs/sso.md](docs/sso.md)).

**Админка и приложение.** В приложении справа вверху — кнопка «Админка» (для тех, у кого она есть);
в админке справа вверху — «Приложение реестра →», и он же первый пункт меню пользователя. Реестр
везде называется своим именем и со своим логотипом: в заголовках, на странице входа, в письмах и
служебных страницах; ссылки на сайт, поддержку и «О программе» платформы из меню убраны.

- **Обзор** — главные риски одной страницей: доступ у неработающих (по системам), учётки без
  сотрудника, конфликты полномочий, привилегированный доступ, лишние и недостающие доступы,
  исключения и их сроки, соответствие ролевой модели, риски процессов, состояние источников.
- **Руководству** — дашборд для руководства, только цифры, без списков людей и учёток: главные
  показатели с изменением за период (7, 30, 90 дней, год) и мини-графиком; графики динамики по
  дням (наведите — значение на дату; «Таблицей» — все цифры по дням с выгрузкой в CSV); разрез по
  1С, AD и Битрикс24 (доступ у неработающих, учётки без сотрудника, доля учёток, привязанных к
  сотрудникам); соответствие ролевой модели; ход пересмотра доступа; свежесть источников. Кнопка
  «Печать» — страница без меню. Для графиков реестр каждый час сохраняет показатели дня
  (`Registry Metric Snapshot`, одна запись на день, остаётся последний подсчёт): динамика
  накапливается с момента установки обновления.
- **Сотрудники** — поиск и фильтры (организация, статус, «уволен, но доступ есть», «роли 1С в
  обход профилей», «админ Битрикс24»). Карточка сотрудника: кадры, все учётки в 1С, AD и
  Битрикс24 с правами, доступ к разделам Битрикс24, роли доступа и роли в процессах, сверка
  «положено / есть». Владелец ролевой модели прямо из сверки согласует лишнее как исключение.
  Общие папки Synology — деревом: сначала только верхние папки (общие ресурсы) с уровнем доступа и
  числом вложенных папок, где у сотрудника свои права; стрелка раскрывает вложенные, «Раскрыть
  всё» — всё дерево. Папка без своих прав показывает права родителя («как у папки «buh»»).
- **Контроль** — списки для работы: доступ у неработающих, конфликты полномочий, лишние доступы,
  привилегированный доступ, учётки без сотрудника, не хватает доступов, исключения и сроки, давно
  не входили, риски процессов, расхождения с кадрами, **кадровые события**: после приёма и
  перевода — что выдать по ролям, после увольнения — какие учётки отключить и что отозвать
  (кнопка «Обработано» отмечает событие). Каждый список фильтруется, сортируется и
  выгружается в CSV (открывается в Excel).
- **Гашение замечаний.** Разобранное и принятое замечание (например, учётка подрядчика в 1С, под
  которую нет сотрудника) отмечается галочкой → «Погасить выбранные» → обязательный комментарий и,
  при желании, дата «погасить до». Замечание пропадает из списка и счётчиков; «Показать
  погашенные» и «Вернуть» (тоже с комментарием) — в том же списке. Гасятся: доступ у
  неработающих, учётки без сотрудника, давно не входили, привилегированный доступ, конфликты
  полномочий, риски процессов, расхождения с кадрами, общие папки. Лишние доступы гасятся не так,
  а исключением (с владельцем и сроком), кадровые события — кнопкой «Обработано».
  **Журнал гашений** («Контроль» → «Разобрано»; в desk — список `Alert Suppression`): что, кто и
  когда погасил и почему, до какой даты, кто и почему вернул. Записи не правятся и не удаляются,
  изменения видны в истории версий; гасить могут администраторы, аудиторы и владельцы ролевой
  модели. После даты «погасить до» замечание возвращается само.
  Погашенное скрыто и в отчётах desk по тем же замечаниям (учётки без сотрудника, вход и
  включённые учётки у неработающих, давно не входили, роли в обход профилей, конфликты
  полномочий, риски процессов, расхождения Битрикс24 и employeeNumber, замечания по папкам):
  над таблицей — «Скрыто погашенных замечаний: N», галочка «Показать погашенные» показывает
  только их, с причиной, кто погасил и ссылкой на запись журнала.
- **Права доступа**, **Роли доступа**, **Бизнес-процессы** — каталоги с карточками: у кого есть
  право, кто получает роль и почему, участники и риски процесса.
- **Пересмотр доступа** — задания проверяющего: по каждому сотруднику его доступы и кнопки
  «Оставить» / «Отозвать» (или «Оставить всё»); ход кампаний и список на отзыв.
- **Источники** — когда и с каким результатом загружались ЗУП, 1С, AD и Битрикс24.
- **Отчёты** — те же отчёты, что в desk (доступы 1С, Active Directory, Битрикс24, общие папки,
  ролевая модель и процессы), но в приложении: с русскими названиями и пояснениями, фильтрами,
  таблицей на всю ширину и выгрузкой в Excel. Ширину колонок меняют перетаскиванием края заголовка
  (двойной щелчок — как было), лишние колонки скрывают кнопкой «Колонки»; настройка запоминается в
  браузере. Длинный текст обрезается «…», полностью — при наведении; заголовок и первая колонка
  закреплены, таблица по высоте помещается в окно. Desk для этого не нужен — достаточно профиля
  доступа с разделом «Отчёты» (можно открыть только часть отчётов). В отчётах о людях к каждому
  сотруднику добавлены организация, подразделение и должность по кадрам (основное место работы) —
  в таблице и в выгрузке в Excel.

Широкие таблицы (сотрудники, «Контроль», права, отчёты) занимают всю ширину окна. В desk реестр
по умолчанию включает полноширинный режим; обычную ширину возвращает пункт «Toggle Full Width»
в меню пользователя.

**Утренняя сводка по почте.** Раз в сутки реестр присылает выбранным людям письмо:
счётчики списков «Контроля» с изменением со вчера; новые замечания поимённо (со ссылками в
приложение) и сколько закрылось; источники, которые не загрузились или не обновлялись больше
суток; изменения прав на общих папках Synology; гашения, у которых срок кончается в ближайшую
неделю; просроченный пересмотр доступа. «Новое» считается от прошлой сводки (в понедельник — с
пятницы); погашенные замечания не учитываются. Настройка — «Access Registry» → «Источники данных» →
**«Утренняя сводка»** (`Registry Digest`): включить, час отправки, только рабочие дни, «не
отправлять, если нового нет», получатели (сводка уходит только пользователям с доступом к
реестру). Кнопки «Предпросмотр» и «Отправить сейчас»; каждая сводка с текстом письма — в
«Журнале сводок» (`Registry Digest Log`). Нужна исходящая почта (Email Account «по
умолчанию для исходящих»); без неё в журнале будет «Ошибка» с объяснением.

Поиск (клавиша `/`) — по сотрудникам, учёткам 1С, AD и Битрикс24, логинам, почте, ролям,
процессам и правам. Даты рождения видят только администраторы и аудиторы.

## Кто работает с реестром

Роли создаются при установке; назначаются в админке: «Пользователи» → карточка → «Роли».
Подробно — в [docs/roles-and-processes.md](docs/roles-and-processes.md#кто-работает-с-реестром).

| Роль | Кому | Что может |
|---|---|---|
| **Registry Admin** | администратор реестра | всё: базы, домены, порталы, загрузки, настройки, данные |
| **Registry Auditor** | служба безопасности, ИБ, внутренний аудит | читает всё, включая даты рождения; ничего не меняет |
| **Access Role Manager** | владелец ролевой модели | права доступа, роли, назначения, исключения, конфликты полномочий |
| **Process Manager** | методолог процессов | бизнес-процессы, роли процессов, участники |
| **Access Catalog Viewer** | главный бухгалтер, руководители, контролёры прав | сотрудники, доступы, роли, процессы, отчёты — без дат рождения и кадровых отсутствий |
| **Access Reviewer** | руководители — проверяющие в пересмотре доступа | только свои задания в `/registry`; может быть пользователем сайта без лицензии рабочего места |
| **1C Sync** | технический пользователь n8n | только методы импорта |

System Manager по-прежнему может всё.

### Доступ к приложению по разделам

Роли выше дают доступ к приложению `/registry` целиком. Чтобы открыть человеку только часть —
**профиль доступа**: `/registry` → **«Доступ к приложению»** (видят администраторы реестра;
в desk — «Источники данных» → «Профили доступа к приложению», `Registry Access Profile`).

- **Разделы и уровни.** Обзор, Руководству, Отчёты, Сотрудники, Права доступа, Бизнес-процессы, Источники, кампании
  пересмотра — открыт или нет. «Контроль» и «Роли доступа» — «просмотр» или «работа»: в
  «Контроле» работа — гасить и возвращать замечания, отмечать кадровые события; в «Ролях
  доступа» — согласовывать лишние доступы как исключения. Отдельно — «персональные данные»
  (даты рождения).
- **Только нужные системы.** «1С», «Active Directory», «Битрикс24», «Общие папки» — чьи данные
  видны (ничего не отмечено — все). Например, администратору NAS — «Общие папки», 1С-нику — «1С».
  Действует везде, где данные делятся по системам: вкладки и учётки в карточке сотрудника и сверка
  в ней, колонка «Учётки» в списке сотрудников, строки списков «Контроля» (список «Общие папки» —
  только с этой системой), каталог прав, отчёты (группы 1С, AD, Битрикс24, папок — только свои; в
  отчётах ролевой модели — строки своих систем), поиск, счётчики и источники на «Обзоре». Проверяется
  на сервере, как и разделы. «Руководству» (только итоговые цифры), бизнес-процессы и конфликты
  полномочий (их стороны бывают в разных системах) не ограничиваются. Утренняя сводка уходит только
  тем, кто видит все системы.
- **Только нужные отчёты.** Для раздела «Отчёты» можно отметить конкретные отчёты (ничего не
  отмечено — все). Отчёты с персональными данными (профиль Битрикс24 с датой рождения,
  отсутствия) открываются только с флажком «персональные данные».
- **Пример: главный бухгалтер** — «Руководству» и «Отчёты» (доступы 1С): красивые отчёты и
  графики без desk и без доступа к спискам людей в «Контроле».
- **Только нужные списки «Контроля».** Например, администратору NAS — «Общие папки» и «Журнал
  гашений»: он видит и гасит только их, в журнале — только свои гашения.
- **Кому.** Пользователи профиля не нуждаются в ролях desk: приложение откроется по профилю, это
  может быть пользователь сайта без лицензии рабочего места. Профили и роли складываются —
  действует наибольший уровень.
- **Проверка на сервере.** Каждый метод приложения проверяет свой раздел и список; скрытая
  кнопка — не защита, защита — в API.
- **Кто что видит.** На той же странице — итоговый доступ каждого пользователя и откуда он
  (роль или профиль). У каждого профиля — **история**: кто, когда и что поменял.

Утренняя сводка показывает все списки, поэтому уходит только тем, кому открыты «Обзор» и весь
«Контроль».

## Раздел «Access Registry»

Рабочее пространство приложения: первый пункт боковой панели, адрес `/app/access-registry`.
Чтобы страница не превращалась в полотно ярлыков, она разбита на **главную и подразделы** —
вложенные страницы в боковой панели.

**Главная** — три коротких блока:

- **Начать отсюда** — приложение реестра, «Обзор доступа», полный отчёт по доступам 1С;
- **Что проверить сегодня** — вход в 1С у неработающих, включённые учётки AD и Битрикс24 у
  уволенных, сверка доступа, конфликты полномочий, новые кадровые события, замечания по папкам,
  неудачные синхронизации;
- **Разделы реестра** — переходы в подразделы.

**Подразделы** (у каждого — одна строка пояснения, ярлыки со счётчиками и справочники с отчётами):

| Подраздел | Что там |
|---|---|
| Кадры | сотрудники, трудоустройства, дерево подразделений; разбор: кандидаты на склейку, новые кадровые события, только совместительство, расхождения и кандидаты в руководители, пропавшие из ЗУП |
| Права 1С | пользователи со входом, не привязанные, вход у неработающих, роли в обход профилей, сироты ИБ, доступ ко всем организациям, профили, журнал изменений прав (см. [Пользователи 1С и права](#пользователи-1с-и-права)) |
| Active Directory | учётки, включены у уволенных, без сотрудника, давно не входили, группы, проставить employeeNumber (см. [Active Directory](#active-directory)) |
| Битрикс24 | пользователи, расхождения с кадрами, доступ к разделам, журнал записи (см. [Битрикс24](#битрикс24)) |
| Общие папки | кто имеет доступ, замечания, общие папки и права папок (см. [Общие папки Synology](#общие-папки-synology)) |
| Ролевая модель | сверка, конфликты, роли, каталог прав, исключения, пересмотр доступа |
| Бизнес-процессы | процессы, роли, участники, риски, импорт из Excel |
| Источники данных | базы 1С, домены AD, порталы, файловые серверы, журнал и неудачные загрузки |

Счётчик на ярлыке открывает список с тем же фильтром; 0 значит, что разбирать нечего.

Раздел часть приложения: при каждом `migrate` главная и подразделы восстанавливаются из
`access_registry/access_registry/workspace/`; правки через интерфейс сохраняются, только если сделаны
в developer mode (тогда они попадают в эти файлы).

## Обзор доступа

Страница `/app/access-overview` (первый ярлык блока «Пользователи 1С и права»). Всё главное на
одном экране, для роли System Manager. Работает в светлой и тёмной теме.

- **Поиск** — по ФИО сотрудника, имени пользователя 1С, логину и логину AD, а также по не
  привязанным учёткам AD.
- **Обзор** — ключевые цифры (работающие сотрудники, пользователи 1С со входом, вход у
  неработающих, не привязанные, роли в обход профилей, сироты ИБ); если подключён домен — отдельная
  строка по AD (включённые учётки, включены у неработающих, отключены в AD при входе в 1С, без
  сотрудника). По клику — список или отчёт. Ниже — что требует внимания (первые записи главных
  проблем) и состояние каждой базы 1С и домена AD: последняя загрузка, ошибки.
- **Сотрудник** — должность, подразделение, основное место работы, трудоустройства, кадровые
  события, учётки AD (включена ли, последний вход, пароль, OU, группы, совпадает ли
  employeeNumber) и все учётные записи 1С во всех базах: логины, организации, профили с раскрытием
  ограничений, роли в обход профилей, состояние учётки AD, под которой входят в 1С. Если сотрудник
  уволен, а вход в 1С разрешён или учётка AD включена, карточка подсвечивается красным.
- **Матрица доступа** — сотрудники × домены AD и базы 1С: в ячейке AD — число групп (× — учётка
  отключена), в ячейке базы — число профилей, красная ячейка — есть роли в обход профилей,
  подсказка — названия профилей. Фильтр по организации и «Только работающие».

«Не привязаны к сотруднику» — люди: служебные пользователи 1С и сироты ИБ туда не входят, у них
свои отметки и отчёты.

## Разбор кандидатов на склейку

Один человек в разных базах ЗУП имеет разные GUID физлица. Реестр сопоставляет людей так:

1. Физлицо источника уже известно (есть строка в **Физлица в источниках**) — это он.
2. Иначе ищется Person с тем же ключом «фамилия | имя | отчество | дата рождения». Ключ
   нормализуется: регистр, ё→е, лишние пробелы, латинские буквы-двойники → кириллица. Если такой
   человек ровно один и у него ещё нет физлица из этой же базы, новое физлицо добавляется к нему.
3. Иначе создаётся новый Person, и при похожих совпадениях появляется **Person Merge Candidate**:
   - «Совпадают ФИО и дата рождения» — например, два физлица-дубля в одной базе;
   - «Совпадают имя, отчество и дата рождения (смена фамилии?)».

Без даты рождения или без имени люди автоматически не сопоставляются.

В форме кандидата:

- **«Склеить B в A»**. Физлица источников B переходят к A. Все ссылки на B в любых DocType
  переводятся на A: трудоустройства, события, отсутствия, руководители подразделений, директора
  юрлиц, другие кандидаты. B удаляется (копия остаётся в Deleted Document), в A пишется
  комментарий. **UUID человека A не меняется**: он потом уйдёт в AD `employeeNumber`.
- **«Это разные люди»**. Пара закрывается и больше не предлагается.

## Как читать Sync Log

Каждый запуск синхронизации одного источника — одна запись Sync Log.

| Поле | Что там |
|---|---|
| Статус | **В процессе**, **Успех**, **Остановлен предохранителем**, **Ошибка** |
| Первая загрузка | запуск шёл без событий |
| Счётчики (`stats`) | JSON по сущностям: `created`, `updated`, `unchanged`, `missing` (пропали из выгрузки), `moved` (подразделение перенесено), `head_updated`, `cancelled` (отменённые отсутствия), `status_updated` (пересчитан статус человека), `linked_by_match_key` (физлицо привязано к человеку из другой базы), события по типам, `guard` (сколько записей в выгрузке и в реестре), `warnings` |
| Предупреждения и ошибки | предупреждения построчно, при ошибке — полный traceback |
| Ответ /meta | снимок регистра состояний и видов состояний на момент запуска |

Журналы хранятся 180 дней, срок меняется в **Log Settings** админки.

Статус и время последней загрузки кадров, прав и журнала видны и в форме базы.

Весь синк источника выполняется **одной транзакцией**. При ошибке или срабатывании
предохранителя всё откатывается: в реестре не меняется ничего, кроме записи Sync Log. Счётчики
такого запуска показывают, что синк успел сделать до остановки (в `stats` есть пометка `_результат`).

Типичные предупреждения:

- вид состояния с категорией «Неизвестно»/«Отсутствует» в `/meta` — в ЗУП есть вид состояния,
  которому расширение не сопоставило категорию. Решения по нему могут быть неверными, стоит
  доработать сопоставление в расширении;
- родитель подразделения не найден в выгрузке — узел повешен на организацию;
- руководитель подразделения (физлицо …) не найден среди сотрудников;
- у организации нет ИНН — юрлицо не назначено;
- отсутствия сотрудника, которого нет среди трудоустройств.

### Предохранитель

Если актуальных (`Нет в выгрузке = 0`) трудоустройств или подразделений источника в реестре не
меньше **минимума записей**, а в выгрузке их меньше, чем `актуальных × (1 − порог/100)`, синк
останавливается без изменений. Обычная причина — сбой или неполная выгрузка на стороне 1С.
Если сокращение ожидаемое (массовое увольнение, чистка справочника):

1. временно поднимите «Допустимое сокращение выгрузки, %» в Access Registry Settings. Нужное
   значение подсказывает текст в Sync Log;
2. запустите загрузку ещё раз из формы базы;
3. верните прежнее значение.

## Пользователи 1С и права

### Что загружается

Из любой базы 1С — ЗУП, Бухгалтерии и других — через расширение `ВыгрузкаПрав_ИТ`:

| Объект | Что это |
|---|---|
| **IB User** | пользователь 1С (карточка справочника «Пользователи») или пользователь ИБ без карточки («сирота»): логин, логин AD, вход разрешён, профили, организации, фактические роли ИБ, роли в обход профилей, привязка к сотруднику |
| **IB Access Profile** | профиль групп доступа и его роли; кнопка «Пользователи с этим профилем» |
| **IB Audit Event** | событие журнала регистрации 1С: изменения пользователей ИБ и справочников «Пользователи», «Группы пользователей», «Группы доступа», «Профили групп доступа» |
| **IB User BIT Right** | права казначейства БИТ.Финанс пользователя 1С (таблица в карточке пользователя): визы, роли исполнителей, доступ к ЦФО и статьям оборотов |

`IB` — информационная база. Во Frappe имя DocType не может начинаться с цифры, поэтому не `1C User`.
Имена полей — как в спецификации (`uid`, `base_code`, `missing_in_source`, `src_hash`). Ключ записи —
`<код базы>:<GUID>`, у сирот — `<код базы>:ib:<UUID пользователя ИБ>`. У каждой записи есть база
(`base_code`) и её конфигурация (`base_configuration`), отчёты фильтруются по обоим.

**Права БИТ.Финанс (казначейство).** В базах с БИТ.Финанс снимок прав содержит раздел `bit`; реестр
его загружает в карточку пользователя 1С (с историей изменений, как профили):

| Часть `bit` | Что это | В реестре |
|---|---|---|
| `visa_rights` | визы: кто согласует заявки (`visa_name`, `visa_kind`, `condition`, `deputy_for`, `direct`, `assigned_to`) | «Виза» — название, условие, кого замещает |
| `executor_roles` | роли исполнителей: «Руководитель ЦФО», «Ответственный за статью оборотов» (`role`, `objects`) | «Роль исполнителя» — роль и её ЦФО или статьи |
| `rls_rights` | доступ по ЦФО и статьям оборотов (`cfo`, `article`, `read`, `write`, `substitution`, `instead_of`) | «Доступ к ЦФО» — ЦФО, статья, чтение/запись, замещение |

Одна и та же виза с разными условиями — разные права. Снимок без раздела `bit` (база без
БИТ.Финанс или старая версия выгрузки) права БИТ.Финанс не трогает. Синтетический пример —
`access_registry/tests/fixtures/itaccess/bit_sample.json`.

Права БИТ.Финанс входят в ролевую модель как обычные права доступа: в карточке права доступа
(система «1С») укажите «БИТ.Финанс: вид» и название — виза «Казначей», роль «Руководитель ЦФО», ЦФО
«Отдел продаж» (база необязательна). Тогда сверка покажет, у кого они лишние, конфликты
полномочий учтут их (например, «Казначей» и «Руководитель ЦФО» у одного человека), а пересмотр
доступа включит их в задания. Пока право не в каталоге, оно видно в «Доступах вне каталога».

**Роли в обход профилей** — роли пользователя ИБ, которых нет ни в одном его профиле (с учётом
профилей, полученных через группы пользователей). У сирот в обход профилей все роли.

**Привязка к сотруднику** (поле «Сотрудник», способ — «Как найден сотрудник»):

1. **Вручную** — поле «Сотрудник вручную» в форме пользователя. Всегда главнее, загрузка его не меняет.
2. **GUID физлица (ЗУП)** — в базах ЗУП: физлицо из карточки пользователя ищется в кадровых данных
   той же базы.
3. **Учётка AD** — в любой базе: по «Пользователю ОС» 1С (`\\CORP\ivanov`) находится учётка AD
   (домен — по NetBIOS-имени в «Домены AD»), а через неё — сотрудник. Ссылка на учётку AD
   сохраняется в пользователе 1С всегда, даже если сотрудник найден по GUID.
4. **ФИО** — в любой базе, в том числе в Бухгалтерии, где физлица свои: ФИО физлица из карточки, а
   если его нет — имя пользователя. Сравнение нормализованное: регистр, ё/е, латинские
   буквы-двойники. Если однофамильцев несколько, выбирается единственный работающий, иначе связи нет.

Почему связь не найдена, написано в поле «Почему не найден» и в отчёте «Не привязаны к
сотруднику». Все учётные записи сотрудника во всех базах видны в его карточке, в разделе
«Учётные записи».

### Настройка

1. В 1С установите расширение `ВыгрузкаПрав_ИТ` (справочная копия модуля —
   [`onec/ITAccess.bsl`](onec/ITAccess.bsl)). У расширения снят флажок «Безопасный режим», в
   публикации включены HTTP-сервисы расширений, создан пользователь `svc_itaccess` со стандартной
   аутентификацией.
2. Для Бухгалтерии или другой базы без кадров создайте запись в «Базы 1С» с этой конфигурацией,
   для ЗУП откройте существующую. В секции «Пользователи и права» включите «Загружать пользователей
   и права» и укажите URL сервиса (`http://<web>/<публикация>/hs/itaccess`), пользователя и пароль.
3. Нажмите **«Загрузить» → «Пользователи и права»**, затем «Журнал изменений прав». Результат — в
   журнале синхронизаций (вид «Права 1С» или «Журнал 1С»).

Дальше по расписанию: снимок прав каждую ночь в 03:00, журнал 1С каждые 15 минут начиная с
последнего загруженного события (с перекрытием в минуту, дубли отбрасываются). Запуск журнала без
новых событий в Sync Log не пишется, время последней загрузки видно в форме базы.

### Импорт

- Снимок загружается одной транзакцией. Ошибка — откат и запись в Sync Log с traceback.
- Запись сохраняется, только если изменились её исходные данные (`src_hash`). Порядок строк в
  ответе 1С не важен. Повторный импорт того же снимка — `changed = 0`, новых версий нет.
- Дочерние таблицы (профили, роли) обновляются по месту: в истории версий видны именно добавленные
  и удалённые строки.
- Пользователь или профиль, пропавший из снимка, получает «Нет в снимке». Вернулся — флаг снимается.
- Работает тот же предохранитель, что у кадровых данных: снимок, в котором пользователей резко
  меньше, чем в каталоге, отклоняется.
- «Папка» у профиля — нет ролей и ни один пользователь на профиль не ссылается.
- Даты журнала приводятся к часовому поясу сайта.

### Отчёты

В разделе Access Registry, блоки «Пользователи 1С и права» и «Справочники и отчёты». Во всех отчётах
по пользователям есть фильтры по базе и конфигурации:

| Отчёт | Кто в нём |
|---|---|
| **Полный отчёт по доступам 1С** (`IB Access Report`) | кто в какой базе с какими правами: сотрудник, должность, подразделение и основное место работы (из кадров ЗУП), база и конфигурация, логин и логин AD, профили, организации с профилем, который их даёт («все — Администратор; ООО «Альфа» — Бухгалтер»: в 1С
организации ограничивают каждый профиль отдельно), роли в обход профилей. Должность, подразделение,
место работы (ООО, АО — сокращённо) и занятость («основное», «внешн. совм.») — короткими. Флажок «По профилям» — строка на каждый профиль с группой доступа и всеми ограничениями. Фильтры: база, конфигурация, организация, подразделение, сотрудник, только не привязанные. Только для System Manager |
| Роли в обход профилей (`IB Extra Roles`) | роли ИБ, которых нет в профилях пользователя |
| Не привязаны к сотруднику (`IB Users Without Employee`) | вход разрешён, сотрудник не найден; причина — в отчёте |
| Вход у неработающих (`IB Login Not Working`) | вход разрешён, а сотрудник уволен, не принят или пропал из выгрузки. Только для System Manager: показывает кадровый статус |
| Сироты ИБ (`IB Orphans`) | пользователи ИБ без карточки |
| Доступ ко всем организациям (`IB All Organizations Access`) | вход разрешён и нет ограничения по организациям |
| Пользователи профиля (`IB Profile Users`) | кто получил выбранный профиль и через какую группу |
| **Права БИТ.Финанс** (`IB BIT Rights`) | визы, роли исполнителей и доступ к ЦФО и статьям оборотов: у кого, условие, замещение, чтение/запись. Фильтры: база, вид, виза или роль, ЦФО, сотрудник, только у неработающих |
| Кто менял права (`IB Rights Changes`) | журнал 1С с фильтрами по дате, автору и типу объекта |

Недействительные пользователи и пропавшие из снимка в отчёты по умолчанию не попадают.

### Роли

Отчёты по правам 1С читают Access Catalog Viewer, Access Role Manager, Registry Auditor и
Registry Admin; «Вход у неработающих» и «Полный отчёт по доступам» — только администраторы и аудиторы.
Технический пользователь внешнего транспорта — роль **1C Sync** (только методы импорта). Все роли —
в разделе [Кто работает с реестром](#кто-работает-с-реестром).

### API для внешнего транспорта (n8n)

Загрузку делает сам реестр, но методы из спецификации доступны, если данные нужно передавать
снаружи. Нужен пользователь реестра с ролью `1C Sync` и API-ключ (User → Settings → API Access →
Generate Keys), заголовок `Authorization: token <api_key>:<api_secret>`.

| Метод | Запрос | Ответ |
|---|---|---|
| `POST /api/method/access_registry.access_catalog.api.import_snapshot` | `{"base_code": "ZUP1", "snapshot": {…ответ /snapshot…}}` | `{"profiles", "users", "orphans", "changed", "missing"}` |
| `GET /api/method/access_registry.access_catalog.api.get_log_cursor?base_code=ZUP1` | | `{"from": "<ISO со смещением>"}` |
| `POST /api/method/access_registry.access_catalog.api.import_log` | `{"base_code": "ZUP1", "payload": {…ответ /log…}}` | `{"inserted", "skipped"}` |

`base_code` — код базы из «Базы 1С» (регистр не важен). При ошибке метод пишет Error Log и возвращает
ошибку. Пользователь без ролей `1C Sync` или `System Manager` получает PermissionError.

## Active Directory

### Что загружается

Реестр сам читает каталог по LDAP или LDAPS (библиотека `ldap3` уже есть в зависимостях платформы).
**Только чтение**: учётка для подключения не должна иметь прав на запись, соединение открывается
в режиме read-only. В AD реестр ничего не пишет.

| Объект | Что это |
|---|---|
| **AD Domain** | домен: серверы LDAP, Base DN, учётка для чтения, фильтры и OU поиска |
| **AD Account** | учётка: логин, UPN, почта, включена, заблокирована, пароль не истекает, последний вход, смена пароля, OU, должность и отдел из AD, руководитель, `employeeNumber`, прямые группы, привязка к сотруднику |
| **AD Group** | группа: область (глобальная, локальная в домене, универсальная), безопасность или рассылка, число прямых участников-учёток, `managedBy`; ручные поля «Под контролем», «Владелец», «Назначение» |

Ключ записи — `<код домена>:<objectGUID>`: переименование учётки и перенос в другую OU не создают
новую запись, а видны в истории версий. Членство — только прямое (`memberOf`), вложенные группы не
раскрываются.

**Привязка учётки к сотруднику:**

1. **Вручную** — поле «Сотрудник вручную». Всегда главнее.
2. **employeeNumber** — если в нём UUID сотрудника реестра (регистр не важен).
3. **ФИО** — `displayName` (или фамилия, имя, отчество), так же, как для пользователей 1С.

После каждой загрузки AD пользователи 1С перепривязываются к учёткам AD и через них к сотрудникам.

### Настройка

1. Заведите в AD сервисную учётку только для чтения (достаточно обычного пользователя домена).
2. «Access Registry» → **«Домены AD»** → новый домен:
   - **Код домена** — короткий постоянный код (`CORP`), входит в ключи записей;
   - **NetBIOS-имя** — как домен записан в «Пользователь ОС» 1С (`\\CORP\ivanov` → `CORP`). По нему
     пользователи 1С находят свои учётки;
   - **Сервер LDAP** — `ldaps://dc1.corp.example.local:636` (лучше) или `ldap://…:389`; несколько
     контроллеров — через пробел, используется первый доступный;
   - **Base DN**, **Учётка для чтения** (`svc_registry@corp.example.local`) и **Пароль**;
   - при необходимости — фильтры и OU, из которых брать учётки и группы.
3. **«Проверить подключение»**, затем **«Загрузить»**. Результат — в журнале синхронизаций (вид «AD»).

Дальше по расписанию: каждый час, в 20 минут. Для LDAPS с сертификатом внутреннего УЦ добавьте
корневой сертификат в системное хранилище, а не выключайте «Проверять сертификат LDAPS».

### Импорт

- Загрузка домена — одна транзакция; ошибка — откат и traceback в Sync Log.
- Сохранение только при изменении данных учётки или группы. **Последний вход и блокировка**
  меняются постоянно, поэтому хранятся, но не создают версий и не считаются изменением.
- Пропавшие учётки и группы получают «Нет в AD».
- Работает общий предохранитель: если учёток пришло резко меньше, чем в реестре, загрузка
  останавливается (обычно это неверный фильтр или OU).

### Отчёты

| Отчёт | Кто в нём |
|---|---|
| Включены у уволенных (`AD Dismissed Enabled`) | учётка включена, а сотрудник не работает. Только для System Manager |
| Учётки без сотрудника (`AD Without Employee`) | включённые учётки без сотрудника (служебные, внешние, не найденные) и причина |
| Давно не входили (`AD Inactive Accounts`) | включённые учётки без входа дольше N дней (по умолчанию 90, «Access Registry Settings») или без входа вообще. `lastLogonTimestamp` реплицируется с задержкой до 14 дней, для отчёта этого достаточно |
| Пароль не истекает (`AD Password Never Expires`) | включённые учётки с флагом «пароль не истекает» |
| Участники группы (`AD Group Members`) | прямые участники выбранной группы и статус сотрудника |
| Отключены в AD, вход в 1С есть (`AD Disabled But 1C Active`) | учётка AD отключена или удалена, а вход в 1С по ней разрешён |
| Проставить employeeNumber (`AD employeeNumber`) | учётки, у которых `employeeNumber` не равен UUID сотрудника. Кнопка **«Скачать скрипт PowerShell»** скачивает `set-employeeNumber.ps1`: без ключа он только показывает, что изменит, с `-Apply` — записывает. Скрипт запускает администратор AD, реестр в AD не пишет |

Проставлять `employeeNumber` имеет смысл после разбора кандидатов на склейку: UUID сотрудника не
меняется, и дальше привязка не зависит от ФИО.

Проверка без контроллера домена: `python3 tools/generate_synthetic.py … --ad` пишет
`ad/directory.json` с учётками тех же людей, загрузить его в домен:

```bash
bench --site dev.localhost execute access_registry.active_directory.sync.load_directory_file \
    --kwargs "{'domain': 'CORP', 'path': '/tmp/zup_big/ad/directory.json'}"
```

## Битрикс24

### Что загружается

Реестр сам читает портал через **REST API** (входящий вебхук) и, для коробки, через **скрипт
выгрузки прав** [`bitrix24/registry_export.php`](bitrix24/registry_export.php): REST не отдаёт права
ролей CRM, права на папки общих дисков, группы пользователей и график отсутствий.

| Объект | Откуда | Что это |
|---|---|---|
| **B24 User** | REST `user.get` (+ логин из скрипта) | пользователь: ФИО, почта, активен, тип (сотрудник, экстранет), администратор портала, должность, подразделения, последний вход, дата рождения, привязка к сотруднику и учётке AD |
| **B24 Department** | REST `department.get` | подразделение, руководитель, сопоставление с подразделением кадров |
| **B24 Workgroup** | REST `sonet_group.get`, `sonet_group.user.get` | группа или проект, участники с ролями (владелец, модератор, участник) |
| **B24 Access Grant** | скрипт выгрузки, REST `crm.type.list` | права: роли CRM по разделам (сделки по воронкам, лиды, контакты, смарт-процессы), права на папки общих дисков, группы пользователей (администраторы). Кому выдано — код доступа Битрикс24 и его расшифровка |
| **B24 Absence** | скрипт выгрузки | записи графика отсутствий |
| **B24 Write Log** | реестр | что реестр записал в профили |

**Привязка пользователя к сотруднику:** вручную → UUID сотрудника в пользовательском поле портала →
учётка AD (по логину из скрипта или по почте) → ФИО → фамилия и имя, если отчество в Битрикс24 не
заполнено (так находятся те, кому реестр допишет отчество). **Подразделения** сопоставляются с
кадрами по названию (при одинаковых названиях — с учётом родителя) или вручную.

«Кому выдано» раскрывается до людей: `U` — пользователь, `D` / `DR` — подразделение (с
подотделами), `G` — группа пользователей, `SG…_K` — участники рабочей группы, `AU` — все сотрудники.

### Запись в профили

Если в портале включено **«Записывать данные из кадров»**, после каждой загрузки реестр
записывает активным сотрудникам (`user.update`):

- **отчество** — из кадров;
- **дату рождения** — полную дату; скрыть год в профилях — настройкой портала;
- **UUID сотрудника** — в указанное пользовательское поле (например `UF_USR_REGISTRY_ID`, создайте
  его на портале). После этого связь с сотрудником не зависит от ФИО.

Режим «Только пустые» ничего заполненного не трогает; «Пустые и отличающиеся» исправляет по кадрам.
Предохранитель «Не больше изменений за загрузку» (по умолчанию 300): если нужно больше, не пишется
ничего, причина — в журнале синхронизации. Каждое записанное значение — в **B24 Write Log** (было,
стало, ошибка). Значения видят только администраторы и аудиторы.

### Настройка

1. На портале: «Разработчикам» → «Другое» → «Входящий вебхук» от имени администратора, права
   `user`, `department`, `sonet_group`, `crm`. Для записи в профили нужен администратор.
2. Для коробки: скопируйте `bitrix24/registry_export.php` в `/local/registry/export.php`, впишите
   в `REGISTRY_TOKEN` длинную случайную строку (`openssl rand -hex 32`). Скрипт только читает.
3. «Access Registry» → **«Порталы Битрикс24»** → новый портал: код (`B24`), адрес вебхука, адрес и
   ключ скрипта выгрузки. **«Проверить подключение»** покажет права вебхука и что вернул скрипт:
   сколько ролей CRM, назначений, прав на папки, групп и отсутствий, версии модулей и ошибки по
   разделам. Без скрипта загружаются только пользователи, подразделения и группы — в журнале
   синхронизации об этом будет предупреждение. Если скрипт не смог прочитать раздел (например CRM),
   права этого раздела остаются прежними, а причина пишется в журнал.
4. **«Загрузить сейчас»**. Результат — в журнале синхронизаций (вид «Битрикс24»). Дальше — каждый
   час, в 40 минут (после AD: пользователи находят сотрудников через учётки AD).
5. Проверьте привязку («Не привязаны к сотруднику») и только потом включайте запись в профили.

Облачный Битрикс24 ограничивает частоту запросов: пауза между запросами — в настройках портала
(0,5 секунды); ответы «слишком много запросов» реестр повторяет сам. Для коробки паузу можно
убрать. Скрипт выгрузки для облака недоступен — там будут только данные REST.

### Отчёты

| Отчёт | Что показывает |
|---|---|
| Активны у неработающих (`B24 Active Not Working`) | активен в Битрикс24, а по кадрам не работает |
| Не привязаны к сотруднику (`B24 Users Without Employee`) | активные сотрудники Битрикс24 без пары в кадрах и причина |
| Профиль не как в кадрах (`B24 Profile Differences`) | отчество, дата рождения, должность, подразделение отличаются от кадров |
| Руководители: Битрикс24 и кадры (`B24 Department Heads`) | руководитель подразделения в Битрикс24 и в кадрах: совпадает, отличается, не указан |
| Структура: расхождения (`B24 Structure`) | подразделения Битрикс24 без пары в кадрах и подразделения кадров с работающими сотрудниками без пары в Битрикс24 |
| Отсутствия: расхождения (`B24 Absence Differences`) | отпуск или болезнь есть в ЗУП, но нет в графике отсутствий, и наоборот |
| Доступ к разделам Битрикс24 (`B24 Section Access`) | кто фактически имеет доступ к CRM, смарт-процессам, папкам общего диска; фильтр «только неработающие» |
| Участники групп и проектов (`B24 Workgroup Members`) | участники с ролью и статусом сотрудника |

**Структура смарт-процессов.** Карточка портала → «Структура смарт-процессов» собирает в фоне
(очередь `long`, нужен запущенный воркер) JSON-файл и прикладывает его к карточке портала; когда файл
готов, появляется ссылка «Скачать файл». В файле — описание смарт-процессов: типы, воронки и стадии, поля (код, тип, название, варианты списков) и
число элементов. Самих записей и их значений в файле нет — его можно отправить разработчикам, чтобы
решить, какие данные смарт-процессов показывать в реестре. Вебхуку нужен доступ `crm`; если к
какому-то смарт-процессу прав нет, в файле у него будет поле `error` с `ACCESS_DENIED`.

Проверка без портала: `python3 tools/generate_synthetic.py … --bitrix24` пишет `b24/portal.json`,
загрузить его:

```bash
bench --site dev.localhost execute access_registry.bitrix24.sync.load_portal_file \
    --kwargs "{'portal': 'B24', 'path': '/tmp/zup_big/b24/portal.json'}"
```

При загрузке из файла запись в профили никуда не отправляется, только попадает в журнал.

## Общие папки Synology

### Что загружается

На NAS по расписанию работает **сборщик** [`synology/registry_collect.sh`](synology/registry_collect.sh)
(bash, от root). Он **только читает**: `synoshare --get` — права общей папки в DSM,
`synoacltool -get` — Windows ACL папок, и отправляет сырой текст в реестр. Весь разбор — в реестре.

| Объект | Что это |
|---|---|
| **File Server** | NAS: код (он же `SERVER_CODE` в сборщике), домен AD, последняя загрузка, настройки сборщика |
| **File Share** | общая папка: путь, описание, права DSM (чтение/запись/запрет) с расшифровкой в учётки и группы AD |
| **Folder ACL** | папка, права которой **отличаются** от родительской: глубина, наследование, записи ACL (кому, разрешить/запретить, уровень, унаследовано ли), замечания. Изменения прав хранятся в истории версий |

**Какие папки записываются.** Корень каждой общей папки — всегда. Подпапка — только если её права
отличаются от прав родителя; одинаковые права не записываются, поэтому дерево из тысяч папок
занимает в реестре десятки записей — ровно точечные настройки. Режим обхода — `STOP_ON_SAME`:

- `STOP_ON_SAME=0` — обходит всё дерево до `MAX_DEPTH` и записывает все места, где
  права меняются. Полная картина; на больших томах идёт дольше.
- `STOP_ON_SAME=1` (по умолчанию) — не спускается в папку, права которой такие же, как у родителя. Быстро, но
  **пропускает** особые права глубже: если `/Отчёты` как у корня, а `/Отчёты/Квартальные/2026`
  открыта лично кому-то, эта папка не попадёт в реестр. Поэтому раз в неделю запускайте полный
  обход (вторая задача в планировщике с копией скрипта, где `STOP_ON_SAME=0`); реестр напоминает
  об этом в журнале.

**Кто реально имеет доступ** (отчёт «Кто имеет доступ к папкам», карточка сотрудника в `/registry`):
меньшее из двух — права общей папки в DSM и ACL папки; учитываются группы AD, в том числе
вложенные (группа в группе), и записи «Все»; запрет для учётки или любой её группы закрывает
доступ. Отключённые учётки AD доступа не дают. Папки, которых нет в реестре, имеют права ближайшей
записанной папки выше.

**Замечания** (отчёт «Замечания по правам папок», «Контроль → Общие папки» в `/registry`): права
выданы человеку напрямую, а не через группу; доступ для всех; запреты; учётки и группы, которых нет
в AD (удалённые сотрудники); локальные учётки NAS; отключённое наследование; доступ у
неработающих; папки, права которых сборщик не смог прочитать.

### Настройка

1. В реестре: пользователь для сборщика (например `nas-collector@…`) с ролью **1C Sync**, у него —
   «Настройки API» → сгенерировать ключи.
2. «Access Registry» → **«Файловые серверы»** → новый сервер: код `NAS01`, название, домен AD
   (по нему `CORP\ivanov` находит учётку).
3. На NAS: скопируйте скрипт, например в `/volume1/scripts/registry_collect.sh`, заполните в начале
   `REGISTRY_URL`, `API_KEY`, `API_SECRET`, `SERVER_CODE`; при необходимости `SHARES` (только эти
   общие папки) и `SKIP_SHARES`. Если сертификат реестра внутренний — `CURL_OPTS="--cacert …"`.
4. Проверка по SSH: `sudo bash /volume1/scripts/registry_collect.sh --dry-run` — ничего не
   отправляет, пишет файл `/tmp/registry-acl.txt`. Его можно приложить к серверу в поле «Файл
   выгрузки» и нажать **«Загрузить из файла»** — так удобно проверить первую загрузку.
5. DSM → «Панель управления» → «Планировщик задач» → «Создать» → «Запланированная задача» →
   «Пользовательский сценарий», пользователь **root**, ежедневно ночью, сценарий
   `bash /volume1/scripts/registry_collect.sh`. Результат — в журнале синхронизаций (вид «Файловый
   сервер») и на карточке сервера.

Выгрузка без строки `END` (сборщик прервался) не загружается, чтобы не пометить папки пропавшими.
Работает тот же предохранитель от резкого сокращения, что и для AD.

### Отчёты

| Отчёт | Что показывает |
|---|---|
| Кто имеет доступ к папкам (`Share Access`) | сотрудник, папка, уровень (чтение, изменение, полный доступ), через какую запись; фильтры: сервер, папка, путь, сотрудник, «доступ не ниже», «только неработающие и непривязанные» |
| Замечания по правам папок (`Share Permission Issues`) | замечания по папкам и доступ у неработающих |

## Техника (Snipe-IT)

Реестр читает учёт техники из Snipe-IT по REST API и показывает, что за кем числится. В Snipe-IT
ничего не пишет.

### Что загружается

| Объект | Что это |
|---|---|
| **IT Asset** | единица техники: название, инвентарный и серийный номер, категория, модель, статус, место, кому выдана, когда выдана и до какого числа вернуть, аудит, покупка и гарантия, дополнительные поля; привязка к сотруднику. История изменений — кто когда получил и вернул |
| **Snipe-IT User** | пользователь Snipe-IT и сотрудник реестра |
| **IT Asset Event** | журнал действий Snipe-IT: выдача, возврат, аудит, изменение — за «Журнал выдач за, дней» (по умолчанию 180) |

Пользователь Snipe-IT связывается с сотрудником по порядку: «Сотрудник вручную» в карточке →
табельный номер (`employee_num` — табельный номер ЗУП или идентификатор сотрудника реестра) → логин
AD (`username`) → почта (AD или Битрикс24) → ФИО (или фамилия и имя, если такой сотрудник один).
Техника, выданная пользователю, получает его сотрудника.

### Где видно

- **Карточка сотрудника** → вкладка «Техника»: что за ним числится и последние выдачи и возвраты.
- **«Контроль» → «Техника»**: у неработающих; выдана учётке Snipe-IT без сотрудника или
  отключённому пользователю; просрочен возврат («Вернуть до»); просрочен аудит. Замечания гасятся с
  комментарием, как остальные, и попадают в утреннюю сводку.
- **«Обзор»**: «Техника у неработающих», сколько выдано из общего числа.
- **Отчёты** «Техника: у кого что» (фильтры: категория, статус, сотрудник, только выданные, только у
  неработающих) и «Движение техники» (выдачи, возвраты, аудиты за период).
- **Поиск** по инвентарному и серийному номеру.
- **Профили доступа**: система «Техника» — например, для того, кто ведёт учёт техники.

### Настройка

1. В Snipe-IT заведите пользователя только с правами просмотра и выпустите ему ключ API: аккаунт →
   «Manage API Keys». Нужны «Активы: просмотр» и «Пользователи: просмотр»; для журнала выдач и
   возвратов — ещё «Отчёты: просмотр» (Reports: View). Без него техника и пользователи загружаются,
   а в журнале синхронизации будет предупреждение.
2. Админка → «Техника» → «Серверы Snipe-IT» → новый: код (например `SNIPE`), адрес (без `/api/v1`),
   ключ API. «Проверить подключение» покажет число единиц техники и пользователей.
3. «Загрузить сейчас»; дальше — каждый час в :25. Ход загрузки — в журнале синхронизаций (вид
   «Snipe-IT»), предохранитель от резкого сокращения выгрузки такой же, как у других источников.
4. Проверьте «Пользователи Snipe-IT» без сотрудника и привяжите вручную тех, кого реестр не нашёл.

Сеть: реестр → Snipe-IT по HTTPS (443).

## Техподдержка (смарт-процесс Битрикс24)

Раздел приложения «Техподдержка» — снимок заявок, которые ведутся в смарт-процессе Битрикс24:
сколько открыто и просрочено, у кого сколько в работе, сколько ждут, как быстро закрываются и
укладываются ли в срок, динамика по дням и список открытых заявок со ссылками в Битрикс24. В карточке
сотрудника появляется вкладка «Заявки» — его обращения.

**Настройка.** Админка → «B24 Smart Process» → новый: портал и ID смарт-процесса (`entityTypeId`
из файла «Структура смарт-процессов», например 1210). Поля «Кто обратился», «Категория», «Источник»,
«Срок» и «Дата выполнения» можно не заполнять: при первой загрузке они подбираются по типу и
названию поля и сохраняются в карточке — проверьте их и при необходимости поправьте.

**Что загружается.** Только состояние заявки: номер, название, стадия, категория, источник, кто
обратился, ответственный, даты создания, смены стадии, срок и дата выполнения. Описание проблемы,
файлы, комментарии и переписка не читаются. Открытые заявки загружаются все, закрытые
(стадии «успех» и «провал») — за «Закрытые заявки — за, дней» (365 по умолчанию). Загрузка каждые
15 минут, журнал — «Sync Log», вид «Смарт-процессы Битрикс24». Вебхуку портала нужен доступ `crm`.
Если Битрикс24 вдруг вернул ноль заявок, а в реестре их больше десяти, загрузка останавливается
предохранителем и ничего не меняет.

**Кто видит.** Роли реестра — как и другие разделы; для остальных — галочка «Техподдержка» в профиле
доступа («Доступ к приложению»).

## Ролевая модель и бизнес-процессы

Подробно, с объяснением, почему должность — не роль, и порядком первоначальной сверки:
[docs/roles-and-processes.md](docs/roles-and-processes.md).

- **Права доступа** (`Entitlement`) — каталог того, что выдаётся: профиль 1С, группа AD, группа или
  проект Битрикс24, роль CRM или папка Битрикс24; владелец, риск, «привилегированное».
- **Роли доступа** (`Access Role`) — наборы прав: базовые (всем работающим), должностные (по правилам:
  должность, подразделение с подчинёнными, организация, только основное место) и дополнительные
  (назначение `Access Role Assignment` на срок). У права в роли — «Обязательно» или «По необходимости».
- **Исключения** (`Access Exception`) — согласованное лишнее со сроком; **конфликты полномочий**
  (`SoD Rule`) — права, которые нельзя совмещать.
- **Бизнес-процессы** (`Business Process`, дерево) — владелец, версия, регламент, схема, описание;
  **роли процессов** (`Process Role`) — RACI, обязанности, нужные права, минимум участников, нужен ли
  заместитель; **участники** (`Process Participant`) — вручную или «все с ролью доступа».

| Отчёт | Что показывает |
|---|---|
| Сверка доступа (`Access Reconciliation`) | положено / есть по каждому сотруднику и праву: не хватает, лишнее, лишнее у неработающих, исключение |
| Конфликты полномочий (`SoD Conflicts`) | у кого права с обеих сторон правила |
| Подбор ролей (`Role Mining`) | какие доступы есть у большинства сотрудников должности; кнопка «Создать черновики ролей» |
| Доступы вне каталога (`Unmanaged Access`) | что выдано, но не описано; «Добавить отмеченные в каталог» |
| Состав ролей (`Access Role Members`) | кто получает роль и почему |
| Участники процессов (`Process Participants`) | кто в какой роли какого процесса |
| Риски процессов (`Process Continuity`) | роли без участников, без заместителя, с уволенными |
| Результаты пересмотра (`Access Review Results`) | решения проверяющих, список на отзыв, задания без решения |

### Пересмотр доступа

Раз в квартал или полгода руководители (или владельцы прав) подтверждают, что доступы их
сотрудников нужны. «Access Registry» → **«Пересмотр доступа»** → новый:

- **что проверяем** — все системы или одна, организация, только привилегированные и высокого риска,
  с доступами вне каталога или без;
- **кто проверяет** — руководитель сотрудника (руководитель подразделения основного места работы по
  кадрам, для руководителя — вышестоящий), владелец права или один проверяющий. Проверяющий-человек
  сопоставляется с пользователем реестра по почте из AD или Битрикс24; если не нашёлся — задание
  получает «Проверяющий» из формы;
- **«Начать пересмотр»** — реестр собирает текущие доступы и раздаёт их. Проверяющие работают в
  `/registry` → «Пересмотр доступа»; им достаточно роли **Access Reviewer**;
- ход и итог — в форме пересмотра и отчёте **«Результаты пересмотра»** (фильтр «Отозвать» — список
  для администраторов систем). **«Завершить»** закрывает приём решений.

Реестр ничего не отзывает сам: отзыв выполняют администраторы 1С, AD и Битрикс24; после следующей
загрузки доступ пропадёт и из реестра.

### Бизнес-процессы из Excel

Процессы, роли процессов и участников удобно вести в Excel и загружать целиком.
«Access Registry» → **«Импорт процессов из Excel»** → новый:

1. **«Скачать шаблон»** — книга с листами «Процессы», «Роли», «Участники» и памяткой. В ней уже
   текущие данные реестра (если процессов ещё нет — примеры), поэтому обычный порядок такой:
   скачать → поправить в Excel → загрузить обратно. Тот же файл — кнопка «Скачать в Excel» в
   `/registry` → «Бизнес-процессы».
2. Прикрепите файл → **«Проверить»**: реестр покажет, что будет создано и изменено, или список
   ошибок вида «Лист «Роли», строка 5: процесс «ФИН-09» не найден».
3. **«Загрузить»**. Если есть хотя бы одна ошибка, не загружается ничего.

Как узнаются записи: процесс — по коду, а без кода — по названию; «Входит в» — код или название
(родитель может быть в этом же файле); роль — по процессу и названию; участник — по роли и сотруднику.
Сотрудники и владельцы — по ФИО как в кадрах (однофамильцев — по UUID из реестра). Участие в роли
пишется буквой R/A/C/I, права — названиями из каталога прав через «;». Пустая ячейка ничего не меняет.
Флажок «Удалить участников, которых нет в файле» убирает лишних участников только в процессах,
которые есть на листе «Участники».

Счётчики «Есть у сотрудников» в каталоге прав и «Сотрудников» у ролей пересчитываются каждую ночь
(04:30) и кнопкой; сверка и отчёты всегда считают по текущим данным.

## Как это работает

### Модель данных

| DocType | Что | Имя записи |
|---|---|---|
| Access Registry Settings | настройки (Single) | — |
| Info Base | база 1С: ЗУП (источник кадров) или другая (только пользователи и права) | код базы |
| Legal Entity | сводное юрлицо по всем базам; `director` заполняется вручную | `ИНН-КПП` или `ИНН` |
| HR Organization | организация базы | `<код>:<GUID>` |
| HR Department | дерево: «Все организации» → организации → подразделения | `ROOT`, `<код>:org:<GUID>`, `<код>:<GUID>` |
| HR Position | должность (из `/employees`) | `<код>:<GUID>` |
| Person | сотрудник по всем базам ЗУП; дочерняя таблица Person Source ID; в карточке — трудоустройства, события и учётные записи | собственный UUID4 |
| Employment | трудоустройство (элемент «Сотрудники») | `<код>:<GUID>` |
| HR Absence | отсутствие из `/absences` | `<код>:<СотрудникGUID>:<Код>:<ДатаНачала>` |
| HR Event | кадровое событие; флаг «Обработано» ставят люди | `HRE-…` |
| Person Merge Candidate | спорная пара людей | `PMC-…` |
| IB User, IB Access Profile, IB Audit Event | пользователи, профили и журнал прав баз 1С | `<код>:<GUID>` / md5 |
| AD Domain, AD Account, AD Group | домены, учётки и группы Active Directory | код домена / `<код>:<objectGUID>` |
| B24 Portal, B24 User, B24 Department, B24 Workgroup, B24 Absence, B24 Access Grant, B24 Write Log | портал Битрикс24 и его зеркало, журнал записи | код портала / `<код>:<ID>` / хеш |
| Entitlement, Access Role, Access Role Assignment, Access Exception, SoD Rule | ролевая модель | `ENT-…` / название / хеш |
| Access Review, Access Review Item | пересмотр доступа и задания проверяющим | хеш |
| Business Process, Process Role, Process Participant | бизнес-процессы | хеш |
| Sync Log | журнал запусков | `SYNC-…` |

Правила:

- поля из источника доступны только для чтения, их перезаписывает синк. Ручные поля синк не
  трогает никогда: `manual_head`, `director`, `processed`;
- запись сохраняется, только если значения реально изменились. Поэтому повторный синк без
  изменений в ЗУП не создаёт ни одной версии, а `modified` остаётся осмысленным;
- записи не удаляются: пропавшие из выгрузки получают флаг **«Нет в выгрузке»**;
- у всех основных DocType включён Track Changes. Изменения синка в истории записаны от
  пользователя синка;
- дата рождения человека (и ключи сопоставления, в которых она есть) лежит на permlevel 1, её видит
  только System Manager. Для интеграций с другими системами дайте API-пользователю роль с
  доступом к permlevel 1 у Person.

### Статусы

**Трудоустройство** (по датам на «сегодня»; дата увольнения в 1С — последний рабочий день):
нет даты приёма или она в будущем → «Не принят»; дата увольнения прошла → «Уволен»; дата
увольнения сегодня или позже → «Увольняется»; иначе «Работает»; пропало из выгрузки → «Нет в
выгрузке». `Состояние` из ЗУП хранится справочно в поле «Состояние в ЗУП».

**Человек** (по трудоустройствам во всех базах):

- `status` — «Работает», если хоть одно трудоустройство «Работает»/«Увольняется»; иначе «Не
  принят», если такое есть; «Нет в выгрузке», если все такие; иначе «Уволен»;
- `presence` — «Длительное отсутствие», если все активные трудоустройства в категории
  `ОтпускПоУходу` и `ФактическиРаботает = false`; иначе «На месте». Отпуск, больничный и
  командировка на присутствие не влияют;
- «Только совместительство» — активные трудоустройства есть, но ни одно не основное место работы.

### Кадровые события

Приём, Увольнение, Предстоящее увольнение, Перевод (в подробностях «было → стало»), Уход в отпуск
по уходу и Выход из него, Пропал из выгрузки, Вернулся в выгрузку. События создаются при сравнении
с предыдущим состоянием. При первой загрузке источника событий нет. Отсутствия событий не
порождают, кроме смены присутствия.

### Руководители подразделений

- `zup_head` — из `РуководительФизЛицоGUID`.
- `manual_head` — вручную.
- `head` — итог: ЗУП важнее ручного, источник показан в `head_source`.
- `head_conflict` — ЗУП и ручное заполнены и различаются.
- `head_candidate` — подбирается, если нет ни ЗУП, ни ручного: активный сотрудник подразделения,
  чья должность начинается с первого подходящего ключевого слова; основное место работы важнее
  совместительства. Автоматически кандидат не применяется: для этого есть кнопка «Принять
  кандидата».

## Проверка на реальной базе

1. Подключите источник, выполните первую загрузку и проверьте Sync Log: статус «Успех», разумные
   предупреждения.
2. Сверьте число людей «Работает» по каждой организации с ЗУП, например отчётом по Employment
   (статус «Работает»/«Увольняется», группировка по организации) и по Person.
3. Запустите синк ещё раз без изменений в ЗУП: в `stats` только `unchanged`, в Version нет новых
   записей по DocType модуля.
4. Проверьте, что имена эндпоинтов в расширении совпадают с ожидаемыми: `/organizations`,
   `/departments`, `/employees`, `/absences`, `/meta`. Ключ GUID принимается как `ОрганизацияGUID`/
   `ПодразделениеGUID` или `GUID`.
5. Пользователи и права: после загрузки снимка сравните для нескольких пользователей профили и
   организации с формой пользователя в 1С. Повторная загрузка того же снимка — `changed = 0`.
   Посмотрите отчёты «Не привязаны к сотруднику» (для Бухгалтерии — особенно), «Роли в обход
   профилей» и «Вход у неработающих». Неверные привязки поправьте полем «Сотрудник вручную».
6. Active Directory: сначала «Проверить подключение», затем загрузка. Сверьте число включённых
   учёток с `Get-ADUser -Filter 'Enabled -eq $true' | Measure-Object` (с тем же фильтром и OU) и
   группы нескольких учёток с `Get-ADPrincipalGroupMembership` (там же и вложенные — в реестре
   только прямые). Повторная загрузка — в `stats` только «без изменений» и `last_logon_updated`.
   Посмотрите «Учётки без сотрудника» и «Включены у уволенных», затем «Проставить employeeNumber».
7. Битрикс24: «Проверить подключение» (права вебхука и скрипт выгрузки), загрузка **без записи**.
   Сверьте число активных сотрудников и подразделений с порталом, проверьте «Не привязаны к
   сотруднику» и «Профиль не как в кадрах». Имена полей отсутствий в скрипте (`PROPERTY_USER`,
   `PROPERTY_ABSENCE_TYPE`) и методы `CCrmRole` проверьте на своей версии Битрикс24. Затем включите
   запись в режиме «Только пустые» с небольшим пределом и проверьте B24 Write Log и профили.
8. Ролевая модель: «Доступы вне каталога» → каталог; «Подбор ролей» → черновики; проверка ролей с
   владельцами; «Сверка доступа». Порядок — в [docs/roles-and-processes.md](docs/roles-and-processes.md).
